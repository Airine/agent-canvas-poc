# Agent Canvas 中 Agent 节点（Agent Runtime）可视化方式调研报告

## Executive Summary

本报告调研「agent canvas」中 agent 节点的可视化方式，覆盖三类节点（产物实时可视化、操作可视化、通用 Agent（对话））、三态展示与强弱双链画布形态；调研对象为通用 agent 产品、编排画布、可观测与回放工具、图渲染引擎四类先例。结论均经交叉验证，可直接支撑架构决策。

### 核心结论

#### 结论一：三态展示是行业空档，可整体映射为成熟的 Semantic Zoom/LOD 体系，差异化成立

主流编排画布仅提供折叠/展开两级，三态展示（全局摘要/默认内嵌活窗/专注全屏）无直接先例；但 LOD（Level of Detail，细节层级）已有成熟模式可借用：tldraw 按节点屏幕像素尺寸设阈值并配合空间索引裁剪[^1^]，React Flow 提供按 zoom 切换视图的 Contextual Zoom 示例[^2^]，yFiles 提供三级样式[^3^]，ComfyUI 以低质量渲染阈值降级[^4^]。三态中全局/默认两态可整体映射为成熟的语义缩放/LOD 档位体系，专注态叠加为应用层全屏；各档隐含交互权限变化（只读聚合→观察权→交互权移交），tldraw embed 的「单击选中/双击交互」是权限边界显式化的先例[^5^]。

#### 结论二：双窗格、事件流回放、Plan/Todo 外显、过程透明是四条已被反复验证的行业共识

其一，「对话/推理流+操作画面」双窗格联动是事实标准：OpenHands 以三通道观察同一 runtime[^6^]，Devin、Manus、ChatGPT agent 同形态[^7^]，节点内部须含双视图。其二，回放基于事件流重建而非录屏，字符流体积仅为视频 1/100~1/1000[^8^][^9^]。其三，Plan/Todo 是一等公民 UI，Claude Code 官方 Agent SDK 文档要求应用层消费 tool_use 块自行渲染 todo 进度面板[^10^]。其四，过程透明是信任主要来源：n8n 高亮回归曾引发 issue 风暴[^11^]；接管期间须停止截图以保证凭证不可见[^12^]。

#### 结论三：建议架构主线——统一事件溯源 + 三类节点三种投影 + substrate 持久化，实时与回放同构

产物、操作、通用 Agent（对话）三类节点底层是对同一条 append-only agent 事件流的三种投影（快照序列、环境画面、消息序列），事件模型对齐 OpenTelemetry GenAI 语义约定[^13^]；asciinema 3.0 已验证「录制=实时管道旁路」，实时与回放无需两套系统[^8^]；回放与审计的地基是 append-only[^9^]；NervaFS 全量审计流（带 caller/binding/reason 字段）可充当事件总线与持久化层[^14^]。直接收益是 time travel 零额外成本，且三类节点实现重复度显著降低。

#### 结论四：差异化方向——虚线弱链接升级为可观测的数据面

Factorio 类比的实证教训是价值在速率、瓶颈、吞吐量等一阶指标而非动画[^15^]；BPMN 消息流与 n8n ai_tool 虚线证明边线型可承载执行语义[^16^][^17^]。建议弱链接边挂载消息速率、产物版本引用与滞后告警，排查模式点击虚线打开消息 trace 泳道，使强弱链接之分从图示规范变为调试面，构成相对 Dify/n8n 画布的差异化。

### 调研方法说明

调研按 12 个维度组织，累计不少于 270 次独立检索；来源分 T1（官方文档/规范/论文）与 T2（权威媒体/工程博客）两级采信。High Confidence 结论需至少两个维度以独立来源交叉确认（共 12 条）；五处冲突区均消解为设计策略，仅 React Flow 与 tldraw 选型保留为落地决策点；领域未公开的知识缺口如实保留为未决问题。

综合判断，报告建议 MVP 期采用 DOM 画布 + 三态 LOD + noVNC 操作窗 + 产物 iframe 预览 + 事件流埋点，画布引擎以 React Flow 与 tldraw 双轨验证裁决。

## 1. 行业现状与竞品图谱

本章回答三个问题：面向多 agent 编排的可视化产品，行业已经做了什么、在哪些设计上已经收敛、又留下了哪些尚未被占据的空白。调研覆盖两条产品谱系共 17 款产品：编排画布谱系 9 款（LangGraph Studio、Dify、Coze/扣子、n8n、ComfyUI、Flowise、Langflow、CrewAI Studio、AutoGen Studio），agent 工作台谱系 8 款（Devin、Manus、Kimi OK Computer、ChatGPT agent、OpenHands、MiniMax Agent、Genspark、Factory AI），证据来自官方文档、GitHub issue、学术论文与权威 UX 机构实测，共 46 次独立检索。以下结论中，凡标注「行业共识」者均经两个以上独立来源交叉确认；标注「本报告推断」者为基于证据的分析性判断。

### 1.1 双谱系：编排画布与 agent 工作台

当前与「多 agent 可视化」相关的产品已分化为两条结构迥异的谱系：**编排画布**（orchestration canvas）以节点连线图为载体，服务开发者的工作流搭建与调试；**agent 工作台**（agent workbench）以对话流加计算机画面为载体，服务终端用户对单个自主 agent 的监督。两者的分化不是偶然：workflowbuilder.io 对 LangGraph Studio 用户的调研指出，「可视化和调试我的图」与「让我的产品用户看到并操作这个工作流」在实践中是两个不同的产品[^18^]。这一结构性观察——编排画布偏开发者调试、工作台偏终端用户监督——是理解全章竞品格局的主线。

#### 1.1.1 编排画布谱系：以「画布 = 执行视图」建立信任

编排画布谱系最被验证的设计共识是：把运行时状态直接投影到用户亲手编排的同一张画布上，以此建立信任。行业设计综述将其提炼为「一瞥三问」——一瞥画布即应能回答「什么在跑、什么完成了、什么出错了」，其余信息一键展开[^19^]。这一原则已在头部产品中全员落地：Dify 在画布上高亮执行路径并展示每节点耗时与 token 消耗[^20^]；Coze 试运行时画布实时展示执行状态与单节点消耗时间，可点击任意节点查看该次运行的输入输出[^21^]；n8n 以节点图标绿（成功）/红（失败）/转圈（执行中）标记状态[^11^]；ComfyUI 以绿色边框高亮当前执行节点[^22^]。执行路径高亮与节点状态标记因此不是差异化能力，而是该谱系的入场券。

#### 1.1.2 工作台谱系：收敛于「对话流 + 计算机画面」双窗格

工作台谱系在 2025 年迅速收敛于同一结构：一侧为对话/推理流，另一侧为 agent 操作的计算机画面。Devin 采用「对话流 + Progress/Shell/Browser/Editor 多 tab」，顶部另有 Timelapse/IDE/Browser 视图切换[^23^]；Manus 为 chat 线程加实时 computer view，agent 在搜索、浏览器、终端、文档编辑四个应用间切换[^24^]；Kimi OK Computer 为「左侧聊天框 + 右侧虚拟电脑」[^25^]；ChatGPT agent 在屏幕左侧实时展示操作流程并配虚拟电脑画面[^7^]；MiniMax Agent 以右侧「视窗」实时展示当前进程、Request 与 Response[^26^]。开源侧的 OpenHands 在其 ICLR 2025 论文中将此结构显式架构化：GUI 直连 event stream（事件流），并同时提供 VNC 桌面、非 headless 浏览器、嵌入式 VSCode Web 三种观察同一运行时的通道[^6^]。下表对比五款代表产品的窗格结构与回放能力。

| 产品 | 双窗格结构 | 操作画面形态 | 回放机制 | 介入设计 |
|---|---|---|---|---|
| Devin | 对话流 + 4 tab 面板 [^23^] | Shell/Browser/Editor | Timelapse 进度条定位，事件时间线重建 [^27^] | Interactive Planning 事前审计划；发消息唤醒挂起会话 [^27^] |
| Manus | chat + Computer 四 app [^24^] | 云端 VM 实时画面 | 分享链接 `?replay=1` 完整重放，回放页可二次交互 [^28^] | Take Over 接管并归还控制 [^24^] |
| Kimi OK Computer | 左 chat + 右虚拟电脑 [^25^] | 虚拟电脑操作画面 | `kimi.com/share` 分享链接 [^25^] | to-do 清单 `[x]`/`[-]` 进度外显 [^29^] |
| ChatGPT agent | 活动流 + 虚拟电脑 [^7^] | 截图 + 思考文本 [^30^] | 加速录屏式回顾，无进度条定位 [^30^] | Take over browser；decision gate 事前确认 [^12^] |
| OpenHands | 对话界面 + 三观察通道 [^6^] | VNC/Browser/VSCode Web | event-stream 架构天然支持事件流重建 [^31^] | 随时 interrupt；CLI Esc 暂停 [^6^] |

该表呈现两条规律。其一，回放能力的强弱与底层架构直接相关：采用事件流/事件时间线的产品（Devin、Manus、OpenHands）均实现了可定位、可交互的回放，而以截图为主记录的 ChatGPT agent 只提供加速播放的录屏式回顾，被 Nielsen Norman Group 实测点名其回放「不反映实际时长」且接管窗口低分辨率不可调整[^30^]。NVIDIA 的 ATOF 规范进一步把「事件流须携带足够信息以无损重建 agent 运行过程」写成工程标准，佐证事件流重建而非录屏已成为回放的行业方向[^32^]。其二，介入设计普遍分化为轻量插话、重量接管、审批门槛三级，且 OpenAI 官方明确「接管期间不截图」的隐私设计[^12^]——工作台谱系的竞争焦点已从「能不能跑」转向「人能在多深的粒度上监督与介入」。

#### 1.1.3 节点信息展示现状：基线已齐，密度分层刚开始

编排画布节点的常驻信息已形成稳定基线：图标、标题、输入/输出端口、状态标记四件套，Langflow 的自定义组件规范（display_name/description/icon）是这一基线的典型文档化形态[^33^]。超出基线的信息密度则呈现明显的头部效应：token 消耗与单节点耗时的 on-canvas 展示仅 Dify、Coze 等头部产品做到[^20^][^21^]，Flowise 缺少内置 token/耗时展示、观测需外接 LangSmith/Langfuse，被多篇评测列为短板[^34^]。产物内联预览方面，ComfyUI 是公认标杆——Preview Image 节点直接在节点体内渲染生成图片，KSampler 由后端 `comfy.utils.ProgressBar` 驱动节点内实时进度条，其官方节点文档明确以「40 秒无反馈就像死机」为设计动机[^35^][^36^]；相比之下，Flowise/Langflow 的输出检查收在 Playground 侧栏，Dify/Coze 需点击节点查看面板[^33^][^34^]。老牌节点工作流平台 KNIME 以交通灯三态（黄/绿/红）加「右键输出端口查看产物」的模式运转逾二十年，佐证「状态灯 + 端口级产物查看」是经得起时间检验的稳健形态[^37^]。

### 1.2 执行可视化的能力梯度与共识

#### 1.2.1 节点状态六态模型与「skipped 必须区别于未到达」

节点执行状态的展示已收敛为显式六态模型：running、completed、failed、waiting、skipped、queued，配套字段包括运行中节点的已耗时、完成节点的总耗时、重试次数、等待原因与失败一行摘要；未到达的节点保持中性、不加任何 overlay[^19^]。其中一条被点名的行业教训是：分支未执行的节点若无独立的 skipped 态，会被用户误读为「还没跑到」—— skipped 必须与未到达显式区分[^19^]。状态编码的冗余度同样是血泪教训：n8n 曾以单个小红点标记配置错误节点，排错指南统计的 13 个社区求助帖中约 6 例的根因是用户根本没看到这个过弱的信号[^38^]。行业共识由此形成：状态必须经颜色、图标、位置等多通道冗余编码，单一通道在缩放、色盲与大图场景下必然失效。

#### 1.2.2 单节点调试能力梯度

逐节点调试是 2025–2026 年该谱系的军备竞赛焦点，能力梯度清晰：**LangGraph Studio** 居首，提供 checkpoint time-travel 回放执行历史任意步，并支持在节点执行前后通过 interrupt 直接编辑 AgentState[^39^]；**Dify 1.5.0**（2025 年 6 月）以「Last Run 飞行记录器 + 画布底部 Variable Inspect 变量监视器」实现了最完整的产品化——每个节点自动保存上次成功执行的输入/输出，变量可直接编辑后只重跑单个节点，官方将其类比为「在 Jupyter Notebook 中运行单个单元」[^40^]；**n8n** 的 pin data + test step 机制同类但更原始，「修改节点后必须从起点重跑」是高频社区抱怨（issue #13767）[^41^]；**Coze** 支持点击任意节点查看该次试运行输入输出，但不能从任意点续跑[^21^]；**Flowise/Langflow** 仅有 Playground 逐步 trace，偏事后查看[^34^]；**ComfyUI** 不做 step-through，靠输出缓存的增量重算（仅重跑输入发生变化的节点）降低重复调试成本[^42^]。这一梯度说明：「变量缓存 + 单点重放」已被验证为正确架构，且头部产品仍在快速加高壁垒。

### 1.3 现有产品的系统性短板（机会窗口）

#### 1.3.1 大图集体崩坏：规模失控与执行可视化回归

编排画布谱系最一致的短板出现在图规模增大时。Flowise 最被诟病的是「复杂多节点流程视觉混乱、报错信息晦涩」[^34^]；Langflow 被引用最多的抱怨是生产性能与内存问题[^34^]；ComfyUI 的「spaghetti workflow」是公认痛点，甚至催生了 reroute 节点、UE（use everywhere）无线节点、子图折叠、颜色编码等一整套社区自救生态[^43^]。更值得关注的是执行可视化本身的脆弱性：n8n 在 2.14.x 版本出现画布完全不显示执行状态的回归 bug（issue #27961），此前 1.107 版本逐步执行日志消失（issue #18414）、1.123 起节点图标不再点亮，每次回归均引发大量 issue[^11^][^44^]。这从反面证明执行高亮是用户深度依赖的核心功能而非装饰层，其回归测试成本应被当作一等工程问题。此外，Dify 的 Agent 仅支持有向无环调用、复杂多 Agent 协作缺位[^45^]；Coze 存在单工作流 1000 节点、单次 1000 次执行的硬上限[^46^]；AutoGen Studio 官方承认 agent 内部独白可视化不足[^47^]，并自 2025 年 10 月起进入维护模式[^48^]。

#### 1.3.2 工作台谱系的公认痛点：对应关系、结果割裂与版本缺失

工作台谱系的短板同样呈系统性。Thoughtworks 的 HCI 分析点名 Manus、Gemini Deep Research 类产品三大通病：多模块信息对应关系不清晰（对话、进度、代码、结果整合在一屏却难以互相对应）、结果呈现割裂（产物分散在多窗口甚至多平台）、缺乏历史版本管理（无法追溯、比较与回滚，修改意见只能回对话框打字描述而无法在结果上直接标注）[^49^]。体验层面的量化证据同样醒目：Answer.AI 实测 Devin 早期版本 20 个任务仅 3 个成功、14 个失败[^50^]；NN/g 实测 ChatGPT agent 填一个餐厅订位表单耗时 11 分钟，而人类只需约 2 分钟[^30^]；Manus 的 credit 消耗不可预测，多位独立评测指出实际消耗常为官方估算的 2–4 倍[^51^]。换言之，工作台谱系解决了「看得见 agent 在做什么」，却尚未解决「看得懂、改得动、回得去」。

#### 1.3.3 语义缩放与三态的完全缺位

多层级展示是普遍需求，但主流 agent 画布只做了「折叠/展开」两级，且折叠是有损的：ComfyUI 的 collapse 将节点压为只余标题的细条，信息密度完全丢失，并非真正的摘要态[^36^]。真正的语义缩放（semantic zoom，即渲染细节随缩放层级切换）仅出现在独立图引擎 demo（Grafloria 的 high→medium→sketch→low 四级渲染）中，Dify、Coze、n8n、Langflow 的缩放只改变节点像素大小而不改变信息密度[^52^]。下表汇总九款编排画布产品六项关键能力的现状。

| 产品 | 节点常驻信息 | 执行高亮 | 单节点调试 | 多层级展示 | 边语义 | 最大短板 |
|---|---|---|---|---|---|---|
| LangGraph Studio | 节点名/类型色；状态在 checkpoint 面板 [^39^] | 执行路径高亮 [^53^] | time-travel + interrupt 编辑 state [^39^] | Graph/Chat 双模式 [^53^] | 实线=直接/虚线=条件 [^54^] | 强绑 LangSmith、定制天花板低 [^18^] |
| Dify | 图标+标题；状态/耗时/token [^20^] | 画布高亮执行路径 [^20^] | Last Run + 变量面板单点重跑 [^40^] | 节点+配置面板；循环容器节点 | 分支出口 IF/ELIF/ELSE 标签 [^55^] | 仅 DAG、多 agent 协作弱 [^45^] |
| Coze | 图标+标题；黄叹号=缺配置 [^21^] | 实时进度+单节点耗时 [^21^] | 点节点看输入输出，不可续跑 [^21^] | 节点+配置面板；循环容器 | 条件分支出口 | 节点数/并发硬限制 [^46^] |
| n8n | 图标+标题；红点=配置错误 [^38^] | 绿/红/转圈 [^11^] | pin data + test step [^41^] | 固定节点+弹层 | 实线=main/虚线=AI 挂载/红虚线=错误 [^56^] | 执行可视化回归 bug 频发 [^44^] |
| ComfyUI | 端口按类型着色+widget+图片预览 [^36^] | 绿边框+节点内进度条 [^22^] | 输出缓存增量重算 [^42^] | collapse 细条+subgraph+compact [^36^] | 颜色=数据类型、同色可连 [^57^] | spaghetti、学习曲线陡 [^43^] |
| Flowise | 节点+端口，配置在面板 [^34^] | 执行日志/侧栏 | Playground 逐步 trace [^34^] | 无 | 单一线型 | 大图混乱、报错晦涩 [^34^] |
| Langflow | 名称/图标+端口+字段 [^33^] | Playground trace | Playground 逐步检查 [^34^] | 无（字段滚动） | 单一线型 | 生产性能/内存 [^34^] |
| CrewAI Studio | 三类节点（single/crew/router） [^58^] | 执行日志 | step-by-step 控制 | crew 内嵌=天然两级 | router=条件分支 [^58^] | 企业版为主 |
| AutoGen Studio | 画布内联配置+JSON 切换 [^48^] | message flow 流式+暂停 | 暂停/重定向，无 state 编辑 | 无 | agent 间消息边 | 维护模式、独白可视化弱 [^47^][^48^] |

横向阅读该表可见三个结构性空白。第一，「多层级展示」一列全员停留在两级以内：最好的情况是 ComfyUI 的 collapse/subgraph 与 LangGraph Studio 的 Graph/Chat 双模式，没有任何产品实现「全局摘要 / 默认内嵌 / 专注全屏」的三态（三级展示态，下称三态），更无人将细节层级与缩放绑定。第二，能力分布呈哑铃形——调试能力（time-travel、变量重放）与产物内联（进度条、图片预览）各自有单点标杆，但没有产品同时具备两者，单节点调试最强的 LangGraph Studio 恰是定制天花板最低、最难面向终端用户交付的产品[^18^]。第三，边语义虽有「颜色=数据类型」与「线型=关系类型」两套成熟惯例[^56^][^57^]，但边仅承载静态语义，尚无产品在边上挂载速率、消息 trace 等动态运行信息。结合 1.3.1 的大图崩坏与 1.3.2 的对应关系割裂，本报告推断：「无限画布 + 语义缩放三态 + 承载动态语义的边」是当前竞品图谱中无人占据的空档；其中三态的信息架构将在第 2 章展开。

## 2. 节点三态展示的信息架构

第 1 章的调研结论是：主流 agent 编排画布（Dify、n8n、Langflow 等）的节点只有「折叠/展开」两级，缩放只改变像素大小而不改变信息密度，真正的语义缩放（semantic zoom，细节随缩放分层切换）仅出现在独立图引擎 demo 中。本章在此空档上回答：全局、默认、专注三态应如何组织信息与交互、工程上如何实现。核心论点是——三态的本质不是三个缩放级别，而是「信息密度 × 交互权限」的二维矩阵。

### 2.1 三态的本质：信息密度 × 交互权限的二维矩阵

#### 2.1.1 全局 = 零交互只读聚合、默认 = 观察权、专注 = 交互权移交

表面上三态是信息密度的递增序列，但每一态同时隐含一条交互权限边界。全局模式是零交互的只读聚合：节点只呈现身份与状态，用户只能操作画布本身。默认模式授予观察权：内嵌实时任务窗口（下称活窗）（iframe 画面、终端、视频流）可见但不可操作，通过 `pointer-events` 隔离实现「卡片可拖动、窗口不可点」。专注模式完成交互权移交：annotation 写通道打开、VNC 输入事件回传接通、approval 令牌签发，用户从旁观者变为操作者。

三条权限边界在业界均有先例。tldraw 的 embed shape 把「选中态/交互态」做成显式两级模型：单击只是选中形状，双击或 Enter 进入交互模式后指针事件才透传进 iframe，Esc 或点击外部退出——这正是默认模式「观察权」的标准答案，也从根上规避了拖拽节点时 mousemove 被 iframe 吞掉的经典坑（社区解法同样是拖拽期间对 iframe 置 `pointer-events: none`）[^5^][^59^]。只读观察在远程桌面协议层是一等公民能力：docker-selenium 的 noVNC 提供 `SE_VNC_VIEW_ONLY=1` 只读模式，E2B Desktop SDK 可生成 `viewOnly` 只读流链接[^60^]。专注模式的「交互权移交」对应 OpenAI Operator 的 takeover mode——接管期间 agent 停止截图、无法观测用户输入，控制权让渡与观测通道关闭绑定发生[^61^]；approval 签发侧，LangChain 的 HITL middleware 已把人工决策标准化为 approve / edit / reject / respond 四类[^62^]。

| 展示态 | 信息密度（节点内容） | 交互权限 | 权限边界的实现机制 | 活内容档位 |
|---|---|---|---|---|
| 全局模式 | 最低：harness / env / agent id / 标题 + 六态徽章 + 最近产物快照 | 零交互（只读聚合）；仅画布级选择、平移、缩放 | 渲染为轻量占位 DOM；hover 展开详情浮层，不改变节点本体 | 静态快照（最近产物缩略图 / 终端末 N 行） |
| 默认模式 | 中：摘要 + 内嵌实时任务窗口 | 观察权：窗口可见不可操作；单击选中、双击进入交互态 | 非交互态下 iframe `pointer-events: none`；tldraw embed 式双击透传 [^5^] | 限额直播：≤N 个全帧/低帧流，其余心跳帧 |
| 专注模式 | 最高：全屏完整任务界面 + 人工操作面板 | 交互权移交：annotation 写入、VNC 输入接管、approval 签发 | VNC `view_only` 翻转 [^60^]；接管期 agent 观测通道关闭 [^61^]；审批令牌按 interrupt id 签发 [^62^] | 全帧率独占 |

解读：矩阵的关键结构特征是「密度与权限同向但不同步」——从全局到默认，密度跃升而权限只从「无」到「观察」；从默认到专注，密度只是放大，权限却发生质变（移交）。这意味着权限切换才是真正的状态转换事件，视觉放大只是它的伴随动画。表中第三列的机制全部有生产先例支撑，因此三态设计的主要风险不在「能否实现」，而在是否把权限边界建模为显式状态而非隐式副作用：若「放大」与「可操作」耦合（例如仅靠 CSS scale 放大且天然可点），就会同时引入误操作与凭证暴露两类事故。

#### 2.1.2 状态机设计：展示密度与交互权限正交建模

由矩阵可直接推出状态机建模原则：把「展示密度」（global / default / focus）与「交互权限」（none / observe / operate）建模为两个正交维度，而非一个三值枚举。进入专注 = 视觉全屏化（节点 DOM 子树搬迁至全屏容器，不重新挂载，详见 2.3）+ 交互权限申请（VNC `view_only` 翻转、annotation 写通道打开、审批令牌签发）；退出时两者同时回收——视觉搬回原位、写通道关闭、令牌作废。「双回收」缺一即事故：只回收视觉，用户以为退出却仍在向 agent 环境注入输入；只回收权限，则出现「放大了却不能操作」的死态。焦点语义也需同级显式管理：tldraw 官方要求多编辑器场景手动管理 focus/blur，blur 时自动 `complete()` 终止进行中的拖拽/绘制交互，避免半完成的操作悬挂在失焦窗口里[^63^]。

### 2.2 全局模式与默认模式：Semantic Zoom / LOD 的成熟技术储备

#### 2.2.1 按节点屏幕像素尺寸切换详略，zoom 防抖，集中式下发档位

全局与默认两态的切换可以完全落在成熟的语义缩放 / 细节层次（Level of Detail, LOD）技术体系内。该体系的三件标准组件是：其一，阈值用「节点屏幕像素尺寸」而非绝对 zoom 值——tldraw 官方推荐 `shape.props.w * zoom < 50` 时渲染简化版，因为不同尺寸节点在同一 zoom 下理应呈现不同详略；迁移到三态即：屏幕宽 <80px 渲染全局摘要卡，80–400px 渲染默认卡片+活窗[^1^]。其二，zoom 值必须防抖：tldraw 在文档超过 500 个 shape 时启用 `getEfficientZoomLevel()`，相机运动中返回稳定值、停止后才更新真值，否则缩放中途全图重渲染造成卡顿[^1^]。其三，档位由集中式 ViewModeManager 统一下发而非每节点各自订阅 zoom——3D 可视化研究中的 Semantic Zoom Manager 正是「离散档位 + 管理器统一调度」模式，可避免 N 个节点各自监听造成的 N 个订阅与切换不一致[^64^]。

| 框架 / 产品 | LOD / 语义缩放机制 | 档位数 | 阈值基准 | 节点内嵌活内容 | 适配度 |
|---|---|---|---|---|---|
| tldraw SDK | `getEfficientZoomLevel` 防抖 + 内置 shape 低 zoom 简化 + 图片分辨率分级 [^1^] | 连续多级 | 节点屏幕像素宽（如 <50px 简化） | 一等公民 embed shape（iframe，双击交互） | ★★★★★ |
| React Flow | 官方 Contextual Zoom 示例：节点读 zoom 切换内容/占位视图 [^2^] | 2（可自扩展） | 绝对 zoom（社区实践 zoom<0.5 换纯色 div [^65^]） | 任意 React 组件（iframe/视频/终端） | ★★★★★ |
| yFiles（商业） | 三级 detail/intermediate/overview；可按 zoom 切换 WebGL/SVG 渲染器 [^3^] | 3 | 可配 zoom 阈值 | 不面向活内容 | ★★★（结构参照） |
| ComfyUI / LiteGraph | 低质量渲染阈值，默认 zoom<0.6 进入降质模式 [^4^] | 2 | 绝对 zoom（0.1–1.0 可调） | DOMWidget 叠层，需手动同步 | ★★★ |
| Grafloria（demo） | high→medium→sketch→low 随缩放切换真实渲染层级 [^52^] | 4 | 相机 zoom | 无 | ★★（唯一四级先例） |
| n8n / Dify / Langflow | 无：缩放仅改变像素大小，信息密度不变 | 1 | — | 无内嵌活窗 | ★（行业空档） |

解读：对照表呈现出一个清晰的能力断层——通用图引擎（tldraw、yFiles、Grafloria）早已把 LOD 当作基础能力，而 agent 编排画布阵营几乎全体停留在「物理缩放」阶段。这一断层对性能的影响是实打实的：VisualFlow 的工程复盘显示，当用户缩到全局视图时所有节点同时进入视口、视口虚拟化被绕过，1 万节点直接崩溃，必须靠 zoom<0.5 时把复杂 React 组件换成轻量占位节点才能把 DOM 复杂度降低数个数量级[^65^]。对三态设计而言，全局摘要卡本质就是这种 LOD 占位节点，而非「缩小版的默认卡」——两者必须在组件层就是不同的渲染路径。

#### 2.2.2 全局模式内容：身份四元组 + 六态徽章 + 最近产物快照

全局摘要卡的信息取舍遵循「一瞥三问」原则——workflow 可视化研究总结，一瞥画布应能回答「什么在跑、什么完成了、什么出错了」，其余信息一键展开[^19^]。据此全局态保留三类内容：身份四元组（harness、env、agent id、标题）回答「这是谁」；六态状态徽章（running / completed / failed / waiting / skipped / queued，承接第 1 章的共识模型）回答三问；最近产物快照来自「飞行记录器」模式——Dify 1.5.0 为每个节点自动保存上次成功执行的输入输出，官方直接称之为 flight recorder[^40^]。最后一条尤为关键：全局态绝不显示空态，默认展示最近一次运行的产物缩略图，使全局视图在任务结束后仍是有效的结果地图；hover 展开的浮层承载次级信息（已耗时、失败一行摘要、重试次数），不占常态像素。

#### 2.2.3 活节点配额与降级阶梯

默认模式的「内嵌实时窗口」面对一条物理硬约束：「所有节点同时直播」在浏览器内不可行，两条独立证据链共同锁死这一结论。其一，浏览器对隐藏内容的激进优化：display:none、visibility、opacity:0、clip-path 都会导致隐藏 iframe 的 JavaScript 与解码被冻结，唯一可靠的「视觉隐藏但逻辑保活」手段是保持完整渲染并用遮罩盖住[^66^]；而画布虚拟化（tldraw 空间索引裁剪、React Flow 的 `onlyRenderVisibleElements`）恰恰以 display:none / unmount 为手段[^1^][^67^]，即被裁剪节点的活窗必死，活节点必须豁免疫裁剪（tldraw 对选中/编辑中的 shape 即永不裁剪[^1^]）。其二，合成开销：每个被渲染的 iframe 都是独立合成层，ComfyUI 的逐层 profile 显示浏览器 GPU 合成器与 GPU 任务的竞争占生成慢化因素的约 47%、实时预览流另占约 23%[^68^]；ComfyUI 节点 DOM 化后中大型工作流帧率从 60+ 跌至 5 以下，是「每节点一个 DOM 活子树」在规模下失败的直接证据[^69^]。

化解方案是显式的活内容资源管理，即「活节点配额 + 降级阶梯」：默认模式同时直播的节点设上限（如 ≤4 个），其余沿「全帧流 → 低帧流 → 心跳帧 → 快照」降级，用户可手动点亮某节点升入配额。各档均有成熟实现对位：全帧流即 VNC/WebRTC 直播；低帧流降低 captureStream 帧率与分辨率；心跳帧用 CDP `Page.startScreencast`，社区实测约 5fps（headless 下 1fps），恰好适合「证明还活着」的近实时预览[^70^]；快照即飞行记录器的最近产物。降级调度按视口位置与节点优先级自动进行，与 LOD 档位由同一 ViewModeManager 统一仲裁。

### 2.3 专注模式：全屏化的工程铁律

#### 2.3.1 移动 DOM 节点，不重挂载

专注模式最致命的陷阱是重挂载（remount）。若用「在全屏容器里新建一份组件实例」实现放大，iframe 会重载、WebRTC 会断流、终端会话会丢失——用户每次进入专注都在打断 agent 的工作现场。Adobe React Spectrum 关于 fullscreen API 与 Portal 的官方讨论给出了定论式建议：「移动 DOM 节点；不要重定向 React portal 容器，否则 remount、iframe reload、focus loss」[^71^]。据此铁律是：进入时把节点的同一个 DOM 子树（含 iframe / video / 终端）物理搬迁到全屏容器（React 层用 `createPortal` 指向稳定容器或以 ref 直接 appendChild），退出时搬回原位，全程保持渲染、只改布局与尺寸。

#### 2.3.2 真实宽高布局与显式焦点仲裁

第二条铁律是放大必须用真实宽高布局，不能用 CSS transform scale。WebKit 存在长期未修的 bug：CSS scale 放大含 fixed 定位内容的 iframe 会导致整体模糊[^72^]；React Flow 官方亦确认 CSS transform 缩放下「从 DOM 的视角元素尺寸不变」，节点内 canvas 类内容（xterm.js 终端、自绘叠加层）的鼠标坐标需手动乘 $1/zoom$ 校正[^73^]。专注态改用真实宽高重排后，这两个坑同时消失。第三条是焦点仲裁：节点全屏化后，滚轮缩放画布还是滚动 iframe、键盘输入归终端还是归画布快捷键，必须显式设计。tldraw 的多编辑器焦点管理（blur 时自动 `complete()` 终止进行中交互）与画布级 focus mode（`isFocusMode` 隐藏全部 UI）提供了可直接组合的参照：进入节点专注 = 节点 DOM 全屏化 + 画布 isFocusMode + 键盘/滚轮焦点移交，退出时按 2.1.2 的双回收反向执行[^63^][^74^]。

### 2.4 状态可见性的冗余编码原则

#### 2.4.1 多通道冗余编码

三态信息密度不同，但状态可见性是不可降级项。第 1 章 1.2.1 已确立状态信号须多通道冗余编码的原则：节点状态必须颜色 + 图标 + 文本 + 动画多通道并行，任何单通道编码在缩小、色盲、大图场景下都会失效。该原则对全局模式约束最强：摘要卡只剩徽章大小的面积，更需动画（running 脉冲）与形状（failed 描边）等不依赖文字空间的通道，且应为动画提供 reduced-motion 静态降级——Grafloria 为每种动态状态保留静态可供性（static affordance），是易被忽略的可访问性细节[^52^]。此外 skipped 与「未到达」必须可区分，否则分支未执行的节点会被误读为「还没跑到」。

#### 2.4.2 长耗时节点必须显示已耗时与进度

最后一条原则针对 running 态：长耗时节点必须显示 elapsed time 与进度，而非裸 spinner。ComfyUI 的自定义节点文档把动机写得极为直白——「长任务节点让 ComfyUI 像死机一样 40 秒毫无反馈，这就是要加进度条的原因」，其节点内进度条由后端 ProgressBar 驱动 UI 实时百分比[^35^]；workflow 可视化研究同样指出，90 秒的 LLM 调用与挂起节点在默认外观下无法区分，解法是 running 节点上显示已耗时甚至预估时长[^19^]。三态落位：全局态徽章内嵌已耗时计数（如 `running · 42s`），默认态活窗顶部显示进度条与 elapsed time，专注态提供步骤级进度。这与 2.2.3 的降级阶梯不冲突——快照档节点不渲染活内容，但状态徽章与耗时文本仍实时更新，其成本是一个 DOM 文本节点而非一条视频流。

## 3. 产物实时可视化节点

产物实时可视化节点承载 agent 构建的面向人的产物——Markdown 文档、HTML 页面、PPT、表格等。它是第 2 章所述「活窗」的典型实例：默认模式下它是画布上的内嵌活窗，全局模式下按降级阶梯退化为最近一版产物快照，只有进入专注模式才打开 annotation 写通道、把交互权移交给用户。本章回答三个工程问题：产物的每一步变化如何实时渲染、不可信的 AI 生成内容在哪里渲染才安全、多版本与标注反馈如何组织。

### 3.1 流式增量渲染的技术路线

#### 3.1.1 编辑粒度按产物大小路由

agent 修改产物时采用「全量重写」还是「diff 局部编辑」，调研中存在表面冲突，即冲突区（CZ2），但证据收敛于按产物大小与场景路由的混合策略。多方独立实测给出的经验分界约在 400 行：400 行以下全量重写的应用成功率高于 diff，400 行以上重写的 token 成本线性增长而 diff 成功率大致恒定，diff 在经济性与变更可控性上胜出；Aider issue #625、Cursor 内部测试与 Morph fast-apply 三方结论一致[^75^][^76^]。反向证据同样存在：多轮 agent 场景下 diff 格式可靠性下降，每轮重发全文的 whole-code 反而整体最稳；而 unified diff 的支持者强调其锚定精确、失败时响亮报错、便于审计[^77^]。换言之这不是「哪个更优」的问题，而是路由问题：小产物默认全量重写，大产物走 SEARCH/REPLACE 或 unified diff，且编辑应用结果必须显式暴露（applied N of M edits），不允许静默半应用[^75^]。

「全量重写 + 快速应用」的两段式架构正在消解这场争论。Cursor 不让前沿模型直接产 diff，而是由大模型输出修改意图（sketch）、专门的 70B apply 模型用 speculative edits 以约 1000 tok/s 重写全文——比 GPT-4 spec-edits 快约 9 倍、比 Llama-3-70b 朴素推理快约 13 倍[^78^]；第三方实测显示，专用 fast-apply 服务（Morph）应用一次 1000 行文件的重写约 1.3 秒，而前沿模型直接全量重写需 10–12 秒[^76^]。

![fast-apply 与全量重写耗时对比](agent_canvas_sec03_fastapply.png)

规划与应用分离意味着：即使底层是全量重写，配合快速应用层也能在 UI 上做出「局部在变」的体感。此外 OpenAI Canvas 证明用户选区本身就是编辑粒度信号——模型被训练为「用户显式选中文字时倾向 targeted edit，否则倾向 rewrite」，其 targeted edit 成功率较 prompted GPT-4o 基线高 18%[^79^]。对产物节点的含义是双重的：编辑策略层做大小路由，交互层把用户圈选识别为局部编辑意图。

#### 3.1.2 「每步可见」的最优解：结构化增量 + 容错解析

朴素逐字打字机渲染在长 Markdown 流式场景有四个已被工程实践确认的缺陷：字符串拷贝引发 GC 抖动、与 SSE 累加流不兼容、每字符 setState 导致每帧整篇 Markdown AST 重解析进而卡死渲染线程、以及未闭合代码块处解析崩溃造成的剧烈闪烁[^80^]。成熟方案在两个层面补齐：结构容错层以 Vercel Streamdown 为代表——作为 react-markdown 的 drop-in 替代，其 remend 机制自动补全未闭合的加粗、行内代码、链接与标题块[^81^]；高亮层以 @shikijs/stream 为代表，代码 chunk 到达时逐块着色而不重扫全文[^82^]。另一个值得直接借鉴的协议设计来自飞书 CardKit：客户端永远上送全量文本，平台检测新旧文本的前缀关系——新文本以旧文本为前缀则以打字机效果续写尾部，否则全量上屏；客户端自行计算增量反而会触发文字闪现 bug[^83^]。这种「全量快照 + 前缀增量动画」语义把客户端复杂度压到最低，产物节点的渲染层可采用同款协议。

#### 3.1.3 非代码产物：结构化数据流 → 声明式渲染

PPT、文档、表格类产物的成熟路线不是直接渲染流式文本，而是让模型流出结构化数据、客户端声明式渲染。Vercel AI SDK 的 streamObject 按 Zod schema 流出部分 JSON 对象，客户端逐字段渐进渲染；作为对照，LangChain 的 withStructuredOutput 只在完成后给出结构化值，说明结构化流式需要 SDK 原生支持[^84^]。产品侧，Gamma 的流程是「大纲优先 + 卡片并行生成」：先产出可编辑中间大纲（结构修改成本最低的阶段），确认后并行生成全部 slide，30–60 秒出完整 deck[^85^]；Thesys Agent Builder 同样以逐 slide 实时渲染作为 PPT agent 的增量呈现[^86^]。两个来源共同指向：slide/card 是这类产物天然的增量可见单元，节点应以「卡片渐次出现」而非字符流呈现构建过程。最后，「实时」应可关闭：Lovable 官方提供 Live preview 开关，关闭后预览只显示最近完成版本、在变更完成后才更新，避免半成品画面干扰用户[^87^]——产物节点宜提供稳定视图/实时视图双模式。

### 3.2 渲染沙盒

#### 3.2.1 iframe 是行业默认，按产物复杂度分层

不可信的 AI 生成内容必须渲染在浏览器级隔离边界内。Anthropic 官方披露的 Artifacts 架构是 iframe sandbox + 全站进程隔离 + 严格 CSP 限制网络访问，产物托管于独立域[^88^]；v0 官方嵌入模板要求 `sandbox="allow-scripts allow-same-origin"`，但前提是预览运行在代理隔离源上——`allow-same-origin` 保持的是代理源而非父页同源，HMR、cookie、storage 等 origin 敏感能力才得以工作[^89^]。按复杂度分层是共识：单文件产物用 iframe srcdoc 或跨源子域即可；多文件前端项目可集成 Sandpack 这类浏览器内 bundler[^90^]；只有全栈产物才需要 WebContainer 这类 WASM 微操作系统——浏览器 tab 内跑完整 Node.js，毫秒级启动、npm install 比本地快约 10 倍，但只能执行 JS/WASM、无原生扩展[^91^]。Shadow DOM 只做样式隔离、共享 window 全局，不构成安全边界，不可作为唯一防线[^92^]。

#### 3.2.2 安全基线：能力最小化与 srcdoc 消毒

iframe 安全的行业共识是：默认空 sandbox 后逐项加权限；对不可信内容绝不同时授予 `allow-scripts` 与 `allow-same-origin`（两者组合使 sandbox 形同虚设）；并配合 CSP、COOP/COEP 做纵深防御[^92^]。Excalidraw 的 CVE-2024-32472 是这一原则被违反的实证教训：其 web embed 组件将未充分消毒的用户字符串渲染为 iframe 的 srcdoc，叠加为部分嵌入域名开启的 `allow-same-origin`，构成存储型 XSS（CVSS 3.1 评分 6.1），可在宿主域上下文执行任意 JavaScript；修复方式是严格解析输入、手工构造 srcdoc，并将 `allow-same-origin` 收紧到确有需要的服务白名单[^93^]。对产物节点的直接约束是两条：srcdoc 禁止字符串拼接 agent 输出或用户输入，必须经严格转义或 DOM 构造；sandbox 令牌按产物类型逐服务白名单化，而非全局放行。

### 3.3 版本管理与 annotation 交互

#### 3.3.1 版本浏览：默认线性链，双层快照，旧版本编辑即分支

版本浏览 UI 存在四种已产品化的范式，选型取决于产物的迭代深度与协作强度：

| 范式 | 代表产品 | 交互形态 | 适用场景 | 主要局限 |
|---|---|---|---|---|
| 后退按钮（undo 栈） | ChatGPT Canvas [^79^] | 单按钮回退上一版 | 快速试错、单人短会话 | 无法跳转任意版本，无语义信息 |
| 版本选择器（线性链） | Claude Artifacts [^94^] | 底部左角选择器逐版切换 | 单对话内迭代产物 | 无命名、历史不随分享链接暴露 |
| 自动 checkpoint 时间线 | Figma / Notion [^95^][^96^] | 自动快照分组折叠 + 命名里程碑带标题描述，点击只读预览后 Restore | 长周期、多里程碑的产物 | 占用侧边栏，需预览机制配合 |
| 分支树 | storyboard（规划）、Claude 消息分支 [^97^] | 节点带父子链接，可从任意历史状态岔出 | 探索式创作、多方向比较 | 认知成本高，需合并策略 |

四种范式呈明显的复杂度梯度而非互斥选项：后退按钮只解决「改坏了立刻回退一步」，版本选择器解决「同一对话内来回看」，时间线在自动快照之上叠加语义命名（Figma 每 30 分钟自动 checkpoint、用户可命名里程碑[^95^]），分支树则服务于「回到 v3 换个方向重试」的探索式工作流。值得注意的是分支未必以树形 UI 出现——Claude 用「编辑历史消息」隐式产生分支[^97^]，说明分支能力可以先做进数据模型、后做进可视化。对 agent canvas 的建议是默认线性链 + 自动快照/命名里程碑双层，仅当产物支持从旧版派生时才引入树。

版本语义上有两条必须内建。其一，**旧版本编辑 = fork 分支而非覆盖**：Claude Artifacts 中从 v3 发起修改不会覆盖后续版本，而是从该点岔出分支，这是用户明确认可的交互[^94^]。其二，**恢复 = 生成新版本而非销毁当前态**：Figma/Notion 均为「点击版本→只读预览→Restore」[^95^][^96^]，Allo 的恢复确认框默认勾选「把当前版本存入历史」，给恢复操作本身留回头路[^98^]。

#### 3.3.2 版本间 diff：按产物类型分层

diff 视图没有通用形态，应按产物分层。文本文档的主流范式是 Google Docs 建议模式的 inline tracked-changes——插入彩色显示、删除加删除线、边距挂评论卡，且同一份建议数据可渲染三种视图（含建议 / 预览全接受 / 预览全拒绝）[^99^]。代码产物沿用 GitHub 2014 年确立的双模式：unified 适合行级扫读、split 适合结构对照，配合 word 级高亮与未变行折叠；但大改动场景下两种视图同时失效，此时应转向「当前态全览 + 边距变更标记」而非强迫用户读 diff[^100^]。可视化产物（网页/PPT/图片）则有视觉回归工具沉淀的四模式组合：side-by-side 整体对照、wipe 滑块扫读 before/after、onion-skin 透明度叠加发现位移漂移、pixel-diff 确保逐像素不漏[^101^]；配套工程要求是动态区域遮罩与 diff 阈值，否则动画、时间戳等噪声会淹没真实差异[^101^]。

#### 3.3.3 Annotation 的结构化回传：「先指后说」

专注模式下 annotation 写通道打开（第 2 章的交互权移交），核心范式已被 AI 建站工具收敛为「point first, then describe」：v0 Design Mode 以 Cmd+I 进入 inspect，选中元素后用视觉面板或自然语言调整并回写代码；Lovable 把选中元素以 chip 引用形式附加到对话输入，多选累积后与 prompt 一同发送——官方示例「Make this the primary color」即可成句，选区使提示词极短化[^102^][^103^]。标注数据必须结构化回传 agent，公开可见最完整的先例是 Agentation annotation envelope：每条标注携带元素 selector/组件路径、包围盒 bbox、选中文本、computed style 快照、intent 分类、severity 与 pending/resolved 状态机[^104^]。本报告建议产物节点的标注 schema 以此裁剪为最小集：

```json
{
  "id": "ann_9f3c",
  "target": { "selector": "div.slide-3 > h2", "bbox": [120, 84, 460, 52], "quoted_text": "市场规摸" },
  "intent": "fix_typo | restyle | rewrite | move | question",
  "severity": "blocker | normal | nit",
  "status": "pending | resolved | rejected",
  "note": "用户自然语言批注"
}
```

标注还需区分两种寿命：Figma 明确区分 Comments（临时讨论、可 resolve）与 Annotations（永久设计说明、随交付存在）[^105^]——映射到产物节点，「这个按钮颜色不对」是预期被 agent 消费后 resolve 的评论，而「此区域为广告位，勿动」是长期约束 agent 行为的永久标注。评论线程支持 @agent 直接把标注转为指令（Lovable 官方文档确认 tag 即发送指令）[^103^]，标注与指令的边界由此打通。

#### 3.3.4 人机并发防护：pending 不落盘、区域锁可见、冲突高亮裁决

用户在专注模式直接编辑产物、agent 同时继续写入，是产物节点特有的并发风险，工程上已有三层可组合防线。事前：agent 的每轮修改先进入「待审层」而非直接落盘——开源实现 Skycode 为每条 AI 消息保存修改前快照，新增行以 pending 标记插入、删除行以红色覆盖层显示，接受才移除标记、拒绝则从快照恢复[^106^]。事中：agent 正在写入的区域应在 UI 上可见（类比协作者光标避让），且写操作前置校验——pi-diff 的 edit guard 在 agent 提交的 oldText 已不存在于目标文件时阻止写入、强制模型重读，防止过期快照覆盖用户内容[^107^]。事后：同区域冲突时保留双方版本并高亮裁决，WPS 365 的「段落级锁定 + OT/CRDT 自动合并 + 冲突高亮一键选用」是企业级协同的完整参照[^108^]。贯穿三层的底线是「diff, not overwrite」：AI 内容被接受前必须有临时态视觉区分，永不静默覆盖用户内容，且任何 AI 动作可单步撤销[^109^]。另有一个已知缺口必须补齐：Cursor 官方明确 checkpoint 只跟踪 agent 改动、不覆盖用户手动编辑[^110^]——人机双写时用户编辑不在回滚保护内，产物节点的快照机制必须同时覆盖两侧写入，否则「恢复」语义在并发场景下失效。

## 4. 操作可视化节点

操作可视化节点是第 2 章活窗的第二类典型实例，与第 3 章产物节点并列。它承载 agent 的「手」：computer use 桌面、浏览器操作、CLI/bash 任务三类执行现场，需要同时回答三个问题——实时画面用什么流送出来、观察（watch）与接管（takeover）如何切换、历史操作如何回放。本章的调研结论可以概括为一条决策主线：画面流按场景路由而非单选，控制权用「共享会话 + 应用层令牌」两段实现，回放走事件流重建而非录屏——其中「回放基于事件流重建」是 Manus `?replay=1`、Devin Timelapse、OpenHands event-stream 与 asciinema/rrweb/Playwright trace 三条独立证据线收敛出的高置信行业共识。

### 4.1 实时画面流方案选型

#### 4.1.1 MVP 标准答案：noVNC + websockify + x11vnc/Xvfb

画面流选型不应从零权衡，因为 MVP 路线已被四方独立验证为事实标准：Anthropic 官方 computer-use 参考实现的容器就是 Xvfb + Mutter + tint2 + x11vnc + noVNC 的组合，暴露 5900（VNC）与 6080（noVNC）端口，并在 UI 上提供「Toggle Screen Control」按钮供人工接管调试[^111^]；E2B Desktop SDK 的 `stream.start()` 内部同样是 x11vnc + noVNC over WebSocket，并额外提供 `getUrl({viewOnly:true})` 只读链接与 `require_auth` 鉴权[^112^]；docker-selenium 官方镜像内置 noVNC（7900 端口）并支持 `SE_VNC_VIEW_ONLY=1` 只读模式[^113^]；Browser Use WebUI 的社区直播方案亦收敛于同一栈[^114^]。整条链路只需三个组件、几十行启动脚本：浏览器经 WebSocket 连 websockify，websockify 透明转发字节到 VNC server，不做任何渲染。

当 MVP 遇到带宽与多用户瓶颈时，升级路径是替换 server 端为 KasmVNC 而非换协议：webp 编码省约 30% 带宽、WebCodecs 支持 H.264/H.265/AV1 硬解、WebRTC UDP 传输、多用户权限 API，以及打破 RFB 8 字符密码上限的完整用户名/密码 + HTTPS 认证[^115^]。由于 KasmVNC 自带 Web 客户端，前端迁移成本接近于零。

#### 4.1.2 场景路由：WebRTC、CDP screencast 与 DOM 重建的分工

VNC 不是万能答案。四种流方案在延迟、带宽、接管能力上各有明确边界，正确做法是按场景路由：

| 维度 | VNC + noVNC + websockify | WebRTC（mediamtx/KasmVNC UDP） | CDP screencast | DOM 重建（rrweb 等） |
|---|---|---|---|---|
| 端到端延迟 | 受控网络实测 noVNC 约 54 ms [^116^]；公网受拉取式协议约束，帧率上限 ≈1/RTT，150 ms RTT 下更新率降约 10 倍，体验落入数百毫秒–秒级 [^117^] | 典型 200–500 ms，优化管线实测约 267 ms [^118^][^119^] | 200 ms–1 s，实测约 5 fps、headless 仅 1 fps [^70^] | 非实时，live 模式秒级 [^120^] |
| 带宽 | 中高且随画质档可调：TurboVNC 官方数据为 5 Mbps 宽带可传 10–12 百万像素/秒（降质可用），感知无损档需 50–100 Mbps 级网络 [^121^] | 中，H.264 自适应码率 [^118^] | 高，1080p 原始 RGBA 约 8.29 MB/帧，必须压缩 [^122^] | 极低，全量快照 50–200 KB，增量数百字节 [^120^] |
| 画质 | 有损 JPEG 可调，KasmVNC 有 QOI 无损 [^115^] | 视频编码有损，文字边缘略糊 | 逐帧截图，静态画质最高 [^70^] | 重渲染而非像素，Canvas/WebGL 还原受限 [^120^] |
| 实现成本 | 极低，3 组件几十行脚本 [^111^] | 高，信令/ICE/TURN/UDP 端口；借道 mediamtx 降至中 [^118^] | 低–中，几行 CDP 调用 [^70^] | 中，需注入 recorder 与自建 player [^120^] |
| 接管能力 | 原生双向，view_only 一键切只读 [^112^][^113^] | 视频单向，输入需另建 DataChannel/控制通道 [^118^] | CDP Input domain 可注入输入 [^70^] | 基本只读 [^120^] |
| 适用场景 | computer-use 桌面可视化 + 人工接管（默认首选） | 公网多人围观、移动端低延迟演示 | 浏览器 agent 的轻量内嵌预览 | 事后回放、审计 |

从表中可以读出三个路由规则。其一，延迟谱系呈明显的对数分布（见图 `agent_canvas_sec04_stream_replay.png` 右）：终端字符流（xterm.js + WebSocket，10–50 ms）比一切画面流低一个数量级，WebRTC 与局域网 VNC 同处十至百毫秒档，CDP screencast 与公网 VNC 则落入秒级上限——这解释了为何 CDP screencast 只能承担第 2 章降级阶梯中的「心跳帧（近实时预览）」角色，而不能作为专注模式的主画面。其二，接管能力与延迟几乎负相关：延迟最低的 DOM 重建完全只读，而原生双向的 VNC 恰是延迟可接受区间内的唯一双向方案，这从技术上锁定了「takeover 必须发生在 VNC 会话上」的结论。其三，WebRTC 的代价是工程复杂度而非性能：UDP 端口无法走普通 HTTP 反代、严格 NAT 环境需要 TURN、输入回传要另建通道，即媒体面/控制面分离架构——因此它应作为「公网多人围观」的增量能力（借道 mediamtx 单二进制，WHIP 推流/WHEP 拉流），而非默认路径[^118^]。

### 4.2 Watch ↔ Takeover 控制权切换

#### 4.2.1 三段式：同一会话 + view_only 开关 + 控制权令牌

第 2 章已确立「专注模式 = 视觉全屏化 + 交互权限申请」的双维模型，takeover 是交互权限申请的最典型实例。工程上它不需要自研输入锁，而是三段式拼装：第一，VNC/RFB 天然共享同一 framebuffer，agent（xdotool/pyautogui）与人（noVNC 输入）看到同一光标，不存在双光标冲突，真正的冲突只是「双方同时操作」；第二，watch 模式就是一行参数——noVNC RFB 的 `viewOnly` 属性、E2B 的 `getUrl({viewOnly:true})`、docker-selenium 的 `SE_VNC_VIEW_ONLY=1` 均为此设计[^112^][^113^]；第三，takeover 时应用层控制权令牌转给人，且 **agent 侧操作必须硬性失败**。ego-browser 的控制权协议是最清晰的范本：「user is controlling」是一个 hard stop 错误，agent 不得重试、不得路由绕过、不得自动调 `takeOverTaskSpace` 夺回，只能等用户显式确认归还[^123^]。这条「硬性失败不夺回」语义应实现在 harness 层（让 agent 的工具调用直接返回失败），而非写在提示词里——后者无法对抗模型在长任务中的重试倾向。

#### 4.2.2 凭证隐私：接管期间停止截图与录屏

第二条安全语义是「凭证不可见」。行业基准做法来自 OpenAI Operator/ChatGPT agent：takeover 期间不采集、不截图——官方文档原文为「While you control the browser, screenshots are not captured, which helps protect passwords and other sensitive data you enter」[^61^]。注意其实现要点是**前置断流而非事后打码**：进入 takeover 即暂停 computer-use 循环的 screenshot 调用、暂停录制管道，并在视觉上给出明确的「隐私模式」指示；DOM 录制路线则可借鉴 rrweb 的 block/mask 选择器（`input[type="password"]` 默认屏蔽），KasmVNC 更进一步提供服务端 `concealed_region` 画面区域遮蔽——遮罩发生在编码之前，比前端 CSS 遮挡可靠[^115^][^120^]。会话连续性方面，商业 HITL 的工程共识是 handoff 不重启浏览器：保持同一会话、agent 暂停等待、人完成后续跑[^124^]；OpenAI 文档承认 takeover 后「may need to re-establish the run」恰是待优化的反模式[^61^]。

#### 4.2.3 辅助认证/登录：凭证不进 agent 环境

辅助认证场景的安全边界应前移到凭证生命周期：凭证从不进入 agent 环境，而非进入后再遮罩。browser-use 的 `sensitive_data` 机制提供了可直接复用的范式——敏感值以 placeholder 形式出现在提示词与日志中，真实值仅在执行输入动作时由 harness 本地注入[^125^]；Steel 的 `?interactive=true` Live View 与 Browserbase 的「delegate credentials」则把「登录、CAPTCHA、凭证输入」明确列为人工接管的标准场景[^126^][^127^]。登录完成后 cookie/会话状态保留在原浏览器会话中归还 agent 继续使用——这正是 4.2.2 节「同一会话 handoff」的自然推论，也意味着 cookie 无需也不应被导出到 agent 的文件系统。

### 4.3 终端任务与历史回放

#### 4.3.1 实时终端：xterm.js + WebSocket 事实标准

CLI/bash 节点的实时画面不需要任何视频技术：ttyd（C 单二进制）、wetty、tmate Web 端全部收敛到 xterm.js + WebSocket 同一架构[^128^]。延迟构成 = WebSocket RTT + xterm.js 渲染（VS Code 官方优化后可达 60 fps，单帧 <16 ms），同机房下用户侧延迟低于 10 ms，比任何画面流低一至两个数量级（见图右）；多个独立来源的定性结论一致为「接近本地」，虽无权威 benchmark 数字[^129^]。实现上可直接内嵌 xterm.js、后端复用 ttyd 做 PTY→WS 桥；tmux 语义（会话在服务端存活、客户端随时 attach/detach）则天然匹配「agent 长时间 CLI 任务 + 人类随时围观」的拓扑[^128^]。

#### 4.3.2 回放格式：字符流、事件流与 DOM 快照的分工

回放路线的核心权衡是体积、可检索性与可跳转性，四条路线的量化对比如下：

| 回放路线 | 体积（5 分钟会话） | 可检索 | 可跳转 | 实现成本 | 适用面 |
|---|---|---|---|---|---|
| 录屏视频（MP4/WebM） | 大，数十 MB [^130^] | 无（像素） | 仅时间轴拖拽，帧级粗 | 低（ffmpeg） | 通用画面，含 GUI |
| asciinema 字符流 | 极小，数十 KB（约为视频 1/100~1/1000）[^130^] | 强，纯文本可 grep/索引 | marker 章节 + 事件级 seek [^8^] | 低，现成 CLI + player，格式可自生成 | 仅终端 |
| 事件流重建（keystroke/action JSON） | 极小 | 强，结构化 JSON | 强，精确到 action | 中，需确定性模拟器重放 [^131^] | 终端 + 结构化 agent 步骤 |
| DOM 快照 + 增量（rrweb） | 中，快照 50–200 KB + 单次交互增量 200–500 B [^120^] | 强，JSON | 强，事件级 + skip-inactivity | 中，引入 rrweb 三件套 | 网页/DOM 界面 |

图 `agent_canvas_sec04_stream_replay.png` 左的对数坐标直观呈现了这一差距：字符流与事件流比视频小约三个数量级，rrweb 居中，Playwright trace.zip（含每步 DOM 快照与截图，实测 10–50 MB[^132^]）因自包含而接近视频量级。三个设计含义随之成立。第一，asciicast v2 的 NDJSON 结构（header + `[time, type, data]` 事件行）简单到几十行代码即可自生成，且 marker 事件天然支持章节跳转[^8^]；「跳转到 t 时刻」的工程实现就是把 [0, t] 事件喂进一个 headless 终端模拟器（asciinema player 内建的 Paul Williams ANSI parser 即此原理）重建屏幕缓冲[^131^]。第二，字符流的可检索性对 agent 场景有独特价值——可以直接 grep 某条命令出现在哪些历史会话，这是像素视频永远无法提供的能力。第三，asciinema 3.0 已验证「录制 = 实时管道旁路 tap」：`asciinema session -o demo.cast -r -l` 一条命令同时本地直播、远程直播、落盘录制，服务端可把直播流转为常规 recording[^133^]——这意味着实时围观与历史回放共用同一数据格式与播放器组件，不需要两套系统。

#### 4.3.3 Playwright trace viewer 范式与 agent 轨迹回放

回放 UI 的最佳范本是 Playwright trace viewer：单个自包含 trace.zip 内含动作时间轴、每个动作的 before/after DOM 快照、截图 filmstrip、网络瀑布、console 与源码定位，可拖进浏览器纯前端打开（数据不出浏览器，对敏感操作审计友好）[^132^][^134^]。它被好评的根本原因是「确定性 post-mortem 工件」——无需复现失败现场即可完成诊断[^134^]。agent 侧已有同构产品：OpenHands trajectory visualizer 以 action（蓝）/observation（灰/红）时间轴呈现轨迹并支持键盘导航[^135^]，SWE-agent inspector 提供 CLI + Web 双形态逐步浏览 .traj 文件[^136^]。落到操作可视化节点，回放界面的具体形态应为：主时间轴 scrubber 承载结构化 thought→action→observation 序列，每个 step 节点挂 before/after 状态对——终端屏幕缓冲区间（cast 事件段）、文件 diff、浏览器 DOM 快照、网络日志作为「富媒体附件」点击展开；时间轴 bar 长度编码耗时，一眼暴露慢步骤。结构化工单是主索引，字符流与 DOM 快照是从属证据，三者体积都足够小，可以全量常驻。

#### 4.3.4 Time travel 三档实现：快照还原查看→checkpoint 重放→全量环境 checkpoint，按实施价值密度递进

「跳到某一步看当时环境状态」有三档实现，实施成本依次递增，落地顺序应按价值密度递进——即先做成本最低、已能覆盖绝大多数诉求的一档。第一档快照还原查看（成本最低，先做）：Playwright trace 的 before/after DOM、asciinema 屏幕缓冲重建均属此类——确定性查看、不能继续执行，但已覆盖「看当时产物」的绝大多数诉求[^132^]。第二档 checkpoint 重放（LangGraph 模式）：每步持久化 checkpoint，checkpoint 前不重跑、之后真实重跑，支持 fork 改状态探索分支；代价是 LLM 与外部环境的非确定性，社区解法是把模型/工具响应一并录制做确定性回放[^9^]。第三档全量环境 checkpoint（最后做）：Crab 论文给出学术范本——turn 边界按副作用分级（无需/仅文件系统/仅进程/全量），ZFS CoW 快照 + CRIU 进程 dump，checkpoint 成本与 LLM 等待窗口重叠隐藏[^137^]。三档的共性地基是 append-only 事件日志：实时管道旁路落盘（4.3.2）、每步产物快照（4.3.3）与环境 checkpoint 只是同一事件溯源架构上逐步加重的三个投影档位。

## 5. 通用 Agent 节点与根 Coordinator

通用 Agent 节点承载分析、Coding 等以逐条对话推进的任务，其执行过程的呈现方式在行业里已形成两大谱系：一是以 Claude Code、Aider、Codex CLI 为代表的 TUI 派（终端用户界面，Text-based User Interface），在字符终端内做分区渲染；二是以 ChatGPT、Perplexity、Cursor 为代表的结构化 chat 派，在富文本聊天流中嵌入折叠卡片。两派载体不同，但在信息层级、常驻元素与中断控制上收敛出高度一致的惯例。本章先梳理这些惯例对通用 Agent 节点的设计含义，再讨论根 Coordinator 节点如何向用户汇报子 agent——这是 canvas 形态可以把行业痛点转化为原生优势的位置。

### 5.1 对话流的信息层级

#### 5.1.1 渐进式披露三层

「渐进式披露（Progressive Disclosure）」是全行业收敛出的主导模式，按三层组织信息：最终答复永远可见；步骤与推理摘要默认折叠、一键展开；完整 trace 藏在深层开关之后[^138^]。Perplexity 采用 answer-first 层级——答案、内联引用、来源条、相关问题逐层可选，完整来源列表默认折叠，被设计拆解评价为「这种克制让页面保持平静」[^139^]；ChatGPT 的 reasoning 折叠块已成为标准件，OpenHands 的 feature request 直接以 ChatGPT 为参照要求「默认折叠保持界面干净，用户可展开」[^140^]；Claude Code 则把工具输出折叠为 `+N lines (ctrl+o to expand)` 的一行摘要[^141^]。值得注意的是，Cursor 官方工程师确认：聊天中的 thinking 块本来就是模型厂商返回的「推理摘要」而非完整思维链，且折叠的 thinking、terminal、tool call 均不进入 Export Transcript——摘要层与原始 trace 层在产品上是明确分离的两层[^142^]。对长任务，ChatGPT deep research 把「已执行步骤摘要 + 使用的来源」外移到侧边栏，主聊天区只收最终报告，耗时 5–30 分钟的任务完成后以通知召回用户[^143^]。对通用 Agent 节点的设计含义是：默认只渲染「答复 + 步骤摘要行」，细节一律懒加载，节点在画布默认态下不应因 trace 膨胀而撑破布局。

#### 5.1.2 工具调用按类型定制渲染

工具调用必须「按工具类型定制渲染」，且每种状态都要显式设计。Claude Code 为每个工具实现独立的渲染组件：Edit 显示彩色 diff、Grep 高亮匹配、Bash 把命令与输出分离；社区逆向分析指出，每个工具自带调用中、结果、拒绝、错误四种渲染方法，意味着所有可能状态都被显式设计，不会退化成「Something went wrong」式的通用错误页[^144^]。作为对照，Codex 采用统一渲染管线，grep 结果与文件编辑得到相同视觉待遇，被技术评论视为反面教材[^144^]。Aider 代表另一条路线：把可审查性外包给 git，每次修改自动提交，推荐用 `git diff` 审查 AI 改动[^145^]。对通用 Agent 节点的含义是：应为内置任务类型（分析/Coding）预设差异化卡片——Edit 渲染 diff、检索渲染高亮命中、命令渲染「命令/输出」双区——而非一个通用 JSON 块；且每张卡片必须覆盖运行中、成功、拒绝、错误四种状态。

#### 5.1.3 噪音折叠、步骤文案与动画语义

噪音自动折叠是刚需，但折叠阈值必须可配置。Claude Code 默认把多行输出折叠到约 3 行，GitHub 上至少三个独立 issue 要求开放阈值配置——用户共识是「长日志折叠很好，但短的高密度输出（状态表、简报）被误伤」，有用户报告在典型的 30 分钟会话里要按 15–20 次 ctrl+o 只为看到自己的命令输出[^141^]。由此得出的规则是：长输出与日志类（npm install、测试堆栈）默认折叠为「一行摘要 + 行数」，短输出直接展示，并提供全局 verbose 开关与 per-tool 阈值。文案层面，Perplexity 的步骤写「Checking predictions」而非技术名，被 UX 拆解点名「镜像了用户心智模型」[^139^]；步骤标题应统一用动宾短语（Searching…、Editing file X），不用 API 名。动画层面，Claude Code 的 spinner 由主题色渐变红指示停滞、shimmer 以两档速度区分「请求中/思考中」，被评价为「动画即信息」——每个动画都编码了系统状态[^144^]。这与执行摘要与第 1 章「过程透明是信任的主要来源」的发现互为表里：状态信号的冗余编码是信任的低成本来源。

### 5.2 常驻元素

#### 5.2.1 Plan/Todo 吸附式外显

Plan/Todo 不能只是聊天流里的一条消息。Claude Code 的 todo 会随聊天滚动消失，官方仓库的 feature request 明确要求「专用的持久 UI 面板」，并点名 Codex/Copilot VS Code 扩展的持久任务列表为正面范例[^146^]；Manus 把 checklist 固定在右下并显示 `6/6` 进度[^24^]。Claude Code 官方 Agent SDK 文档更进一步，直接给出「消费 tool_use 块、自行渲染进度面板」的范例（`Progress: 2/5 completed` + 当前项标签），即官方预期应用层把 todo 渲染成独立进度 UI 而非日志[^10^]。通用 Agent 节点的 plan/todo 应渲染在输入框上方或侧栏的吸附式（sticky）区域，实时勾选、高亮当前项、可折叠；这对根 Coordinator 尤为关键，因为其 todo 就是整张图的执行大纲。

#### 5.2.2 状态栏惯例

状态栏是成本与状态展示的既定惯例。Claude Code 把 statusLine 做成可编程管道，将 model、cost、context_window、rate_limits 等 JSON 字段喂给用户脚本，催生了整套自定义状态栏生态；社区教程的分组惯例是三行——身份（仓库/分支/模型）、花费与限额（会话成本/限额进度条）、技术（上下文 %、token 进出）[^147^]。官方仓库的 feature request 给出了用户期望的形态：`[claude-opus-4-6] Context: 45% (180k/400k) | Cost: $12.34 | Duration: 1h 23m`，并抱怨中断式的 `/cost`、`/status` 会打断工作流[^148^]。耗时展示区分 API 时长与 wall-clock 时长也是惯例（`/usage` 同时给出两者）[^149^]。节点应有常驻 footer：模型标识 | 上下文 % | 成本 $ | 耗时 | 权限模式，随任务滚动持久可见——上下文占用的可见性还能让「上下文压缩何时发生」变得可预期[^148^]。

#### 5.2.3 中断分级

中断必须分级，且中断成本须低于撤销成本。Claude Code 的键位语义是：运行中按 Enter 输入会排队（当前工具调用完成后送达，不打断）；Esc 立即中断并保留已完成工作；Esc Esc 打开 rewind 检查点菜单，可分别恢复代码或对话[^150^]。Codex CLI 对应的是 Enter 中途转向（steer）、Tab 排队[^150^]。社区逆向分析把这套设计概括为「可观察的自主性」：所有工具调用流式展示，用户能在 agent 走错方向的头几秒就中断，权限弹窗甚至有 200ms 防误触延迟[^144^]。用户研究（N=31）中最直白的诉求是「我需要一个暂停键，当它开始脱轨时」，且「沟通过载」本身是五大可用性障碍之一——用户被进度报告的量淹没[^24^]。三级中断（排队纠偏 → 立即中断 → 检查点回滚）应作为节点控制件的基线配置。

下表对照两派在四个关键维度上的惯例差异及其对通用 Agent 节点的设计含义：

| 对比维度 | TUI 派（Claude Code / Aider / Codex CLI） | 结构化 chat 派（ChatGPT / Perplexity / Cursor） | 对通用 Agent 节点的设计含义 |
|---|---|---|---|
| 工具渲染 | 每工具独立组件：Edit→彩色 diff、Bash→命令/输出分离，四状态显式设计 [^144^]；Aider 走「diff 即交付物」、git 审查路线 [^145^] | 工具调用折叠为一行卡片摘要，展开看参数与结果；thinking 块渲染 provider 摘要 [^142^] | 内置任务类型预设差异化卡片；卡片必含运行中/成功/拒绝/错误四态 |
| 折叠策略 | 输出默认折叠约 3 行 + ctrl+o 展开；阈值不可配引发至少 3 个 issue [^141^] | reasoning 块默认折叠、一点展开；折叠内容不进导出 transcript [^140^][^142^] | 三层披露 + 折叠阈值可配置 + 全局 verbose 开关 |
| 状态栏与成本 | statusLine JSON 可编程生态；用户索取常驻「模型/上下文%/成本/时长」 [^147^][^148^] | 较弱；deep research 把步骤与来源外移 sidebar，完成后通知 [^143^] | 常驻 footer：模型 \| 上下文% \| 成本$ \| 耗时 \| 权限模式 |
| 中断控制 | Enter 排队 / Esc 中断保留进度 / Esc Esc 检查点回滚 [^150^] | 随时打断补充指令、断点续跑不丢进度、可停止并拿部分结果 [^24^] | 三级中断为基线；中断成本须低于撤销成本 |

**表格解读**：两派的差异主要是载体约束的产物，而非理念分歧。TUI 派受字符终端所限，把信息密度压进单行摘要与状态栏，因此最早暴露「折叠一刀切」「状态不可见」的痛点，也最早长出可编程 statusLine 这类补偿生态；chat 派有富文本与侧栏可用，天然把长过程外移出主流，但其 reasoning 折叠块与 TUI 的一行摘要本质是同一层「按需展开」。两派在四个维度上的交集——定制渲染、阈值可配的折叠、常驻成本可见、分级中断——恰好构成通用 Agent 节点的最小惯例集。值得注意的是「中断」一行：TUI 派把中断做成三档键位语义，chat 派把中断做成「打断即对话」的自然语言纠偏，canvas 节点应同时保留两者，因为键盘分级服务高频操作者，自然语言纠偏服务低频监督者。

### 5.3 Coordinator 节点的汇报范式

#### 5.3.1 子任务 = 折叠委派卡片

Coordinator 汇报子 agent 的通行范式是「一行委派 + 可展开嵌套树」。Claude Code 把子 agent 渲染为单行委派卡，形如 `code-improver(Suggest code improvements)`；后台子 agent 进入输入框下方的面板与 `/tasks` 列表，成功即移除、失败保留 30 秒；父会话默认看不到子 agent 的中间过程，只收最终摘要[^151^]。社区对「Coordinator 视角」的共识形态见于官方仓库的高票 feature request：子 agent 卡片默认折叠（一行：名称 + 任务 + Running 状态），点击展开看完整嵌套生命周期——thinking 块、每次 tool call 的参数与输出、最终回传结果[^152^]。更完整的参照系是三种布局取向：Devin 走「委派制 + work log 汇报」，界面围绕派任务设计，完成或需要澄清时才回报[^153^]；Manus 走三栏（任务列表 | 聊天 | 电脑实时视图 + 回放进度条 + checklist），支持 Take Over 接管[^24^]；Magentic-UI 则证明「计划可审、步骤可见、动作可配审批」三件套可以同时成立——所有中间步骤对用户展示、用户可暂停计划并插入反馈、可按动作类型配置审批[^154^]。综合而言，根 Coordinator 节点中每个子任务应渲染为折叠卡片（名称 + 任务描述 + 运行状态 + 耗时/token），展开为独立的嵌套对话流；并行子 agent 聚合为 `/tasks` 式面板；汇报节奏沿用 Devin 的「完成/需澄清才打断」原则，避免 5.2.3 所述的沟通过载。子 agent 上报的审批请求沿用第 2 章确立的 approval 四态（approve/edit/reject/respond），在 Coordinator 会话内聚合呈现而非逐条弹窗。

#### 5.3.2 委派卡片与画布子节点的双向锚定

第 1 章已指出，「多模块对应关系不清晰」是 Manus、Gemini Deep Research 类工作台产品的公认通病：对话记录、任务进度、代码与结果被整合在一个界面里，靠缩小与折叠弱化非核心信息，但模块间的对应关系始终模糊，用户难以跟随，更谈不上及时发现和纠正问题[^49^]。在纯聊天或三栏布局里，这个问题没有结构性解法——对话流与执行现场本质上是两个手工对齐的视图。canvas 形态改变了前提：Coordinator 对话流中的每张委派卡片与画布上的子节点本来就指向同一个子任务，二者应当共享同一数据源，互为「双生视图」。具体设计是双向锚定：点击对话流中的委派卡片，视口平滑飞向对应子节点并短暂高亮其边框；反向点击画布子节点，Coordinator 对话流自动滚动定位到发起该子任务的段落。锚定不止于导航——子节点的六态状态徽章（见 1.2.1，等待审批归入 waiting 态）、边上的数据流动画，应同时反映在对话卡片的折叠行上，使对话流本身就是图结构的实时投影；用户在卡片上展开嵌套对话流，等价于在画布上进入该子节点的专注模式。这一设计把上述行业痛点转化为 canvas 的原生优势：对话流回答「为什么派了这个任务、它汇报了什么」，画布回答「它在整张图里的位置、与谁相连」，两个视图通过共享数据源保证永不失配。委派卡片如何沿边发散为子图结构，是下一章图编排边语义的主题。

## 6. 图编排与强弱链接语义

第 5 章确立了 Coordinator 根节点发散子节点的图形态与双生视图，本章处理这张图上的「线」：边的语义如何视觉编码、运行态如何动起来、层级如何组织，以及 Factorio 式游戏化类比应取舍什么。

### 6.1 边的视觉编码

#### 6.1.1 实线=强/事务、虚线=弱/通信成立，但业界惯例分裂，必须内置图例

用户的映射——实线表示上下游/事务强依赖，虚线表示无事务依赖但存在通信或产物依赖——不是自创约定，而是与两个经典建模规范同构。BPMN 规定跨池/泳道的消息流必须是虚线、起点空心圆、终点空心箭头，与池内实线顺序流严格区分，其语义恰好是「跨越边界的通信而非内部控制流」[^16^]；UML 类图中虚线箭头专用于表示 dependency（客户端指向供应者的弱关系）[^155^]。V8 TurboFan 的 Sea of Nodes 同样把三类边里最弱、最不可直观追踪的 effect（读写顺序副作用）分配给虚线[^156^]。因此「实=重=强、虚=轻=弱」的视觉权重直觉有充分先例支撑。

但必须明确指出：这只是一种惯例而非标准，业界存在两组方向相反的实线/虚线语义。SysML 传统与 MATLAB System Composer 用虚线表示控制流、实线表示对象流[^157^]，而 TensorFlow 数据流图与 ComfyUI 中文教程恰好相反（实线=数据流、虚线=控制依赖）[^158^][^159^]——四类权威来源两两相反，且各方都认为自己的约定「显然」。交叉验证已将此标记为惯例分裂冲突区（CZ1）而非事实冲突，消解方案有二：一是产品内必须内置常驻图例（legend）并在边 hover 时直接显示语义文字，不假设用户自带正确心智模型；二是用冗余编码降低对线型的单一依赖（见 6.1.2）。值得注意的是，线型承载语义在工程上是可行的：n8n 中虚线的 ai_tool 挂载连接与实线 main 连接有真实不同的执行语义——item 不能跨 ai_tool 节点直接传递，必须由 agent 节点中转[^17^]。这证明线型可以是执行模型的投影，而不只是视觉装饰。

#### 6.1.2 多通道冗余编码：颜色+线宽+端口形状

单靠线型区分依赖类型会在缩放、色盲、大图交叉场景下失效。最成熟的先例是 Unreal Blueprint：白色粗执行线（三角箭头端口）承载控制流，按数据类型着色的线（圆形端口）承载数据流，颜色+线宽+端口形状三重冗余[^160^]。Blender 进一步给出了静态/动态语义的分工原则：端口形状承载「节点期望/产出的数据类型结构」，不随连接变化；连线线型承载「实际连接状态」（field 间连线自动画虚线，类型错误画红色实线）[^161^]。对 agent canvas 的建议方案汇总如下表。

| 边类型 | 线型 | 颜色 | 粗细 | 端口形状 | 运行态动画 |
|---|---|---|---|---|---|
| 强链接（上下游/事务） | 实线 | 主色（深灰紫） | 粗（≈2.5 px） | 三角/箭头端口 | 沿路径粒子流，速率∝任务进度 [^160^][^162^] |
| 弱链接（通信/产物引用） | 虚线 | 次要色（浅灰） | 细（≈1.5 px） | 空心圆起点+空心箭头终点 | 稀疏光点，可按边类型过滤开关 [^16^][^163^] |
| 错误路由/失败传播 | 实线 | 红色系 | 中（≈2 px） | 圆点端口+感叹号徽章 | 静态高亮优先，reduced-motion 下全程静态 [^161^][^52^] |

上表有三点值得展开。其一，端口符号直接借用 BPMN 消息流的空心圆/空心箭头体系，使「跨边界通信」在端口层级即可辨认，用户不必追溯整条边的走向才能判断语义[^16^]。其二，三类边在线型、颜色、粗细、端口四个通道上均两两不同，任一单通道失效（如全局缩略态下看不清线型）时仍有其他通道兜底——这与第 1 章节点状态冗余编码的结论一致，且 n8n 的教训（执行高亮回归与「小红点太 subtle」引发 issue 风暴）证明单通道状态信号是已知事故源[^11^][^38^]。其三，错误路由单列一类而非复用弱链接虚线：n8n 即为错误输出路由提供独立连接器并以红色标记（经验观察，官方文档未对连线样式作规范说明），但错误路由的语义是「控制流的分支」而非「弱依赖」，用实线+红色更接近其本质，也避免错误路径被视觉权重降格为次要信息。

### 6.2 运行态可视化

#### 6.2.1 边上动画仅运行态开启：沿路径粒子而非 dasharray 滚动

边上流动画的价值已被验证：n8n 2.0 的执行动画（节点脉冲+数据沿边移动）被评价为「安静地成为新 debugger」——哪条分支触发、哪个节点卡住、重试在哪里发生，一瞥即知[^164^]。但实现选型有明确性能边界：React Flow 默认的 CSS stroke-dasharray 滚动动画在数百条边同时动画时成为 CPU 主瓶颈，生产项目 Liam ERD 被迫重写为「沿路径运动的自定义 SVG 对象」，在保留视觉效果的同时消除了性能损耗[^162^]。UE 生态的 Gridline Blueprints 插件进一步揭示了一个细分需求：用户要求按边类型过滤动画（仅执行线/仅数据线/仅选中节点）[^163^]——这直接支持强链接与弱链接的动画可独立开关。综合建议：动画只在运行/调试态开启而非编辑态常开；采用沿路径移动的光点/粒子；遵守 prefers-reduced-motion 媒体查询，降级为静态状态表达（独立图引擎 Grafloria 已示范「每种动画状态都保留 reduced-motion 下的静态可供性」）[^52^]。ComfyUI 社区的 Animated Links 扩展采用 hover 触发而非全量常开，也是控制视觉噪音的有效策略[^165^]。

#### 6.2.2 虚线弱链接升级为可观测数据面

本章最重要的差异化论点是：虚线弱链接不应停留在 BPMN 式的静态图示规范，而应升级为「可观测的数据面」。依据有三。其一，n8n 已证明线型可承载真实执行语义（见 6.1.1），即边是执行模型的一等投影[^17^]。其二，多 agent 通信可视化的实证教训是：实时粒子流适合演示，排查问题时用户要的是时间轴+可回放——A2A 生态的 Trace 工具以 task 生命周期（submitted→working→completed/failed）为最小单元渲染 agent 间通信[^166^]。其三，泳道（swimlane）视图被社区明确提出用于「每条并行 trace 一条 lane、共享时间轴、一眼看重叠」，主流工具落地尚少，是差异化机会[^167^]。具体设计：虚线边上常驻消息速率（msg/min）与最近消息预览；产物引用边上标注版本链路（artifact v3 → 下游节点），当上游已产出 v5 而下游仍在消费 v2 时触发滞后告警；排查模式下点击虚线边，打开该通信通道的消息 trace 泳道时间轴，与第 7 章的事件溯源底座共享数据源。这使强弱链接之分从「画图规范」变成「调试面」，是画布相对 Dify/n8n 的差异化能力。

#### 6.2.3 Factorio 心智的取舍：要一阶指标，不要物理布局成本

Factorio 类比的实证结论需要拆开两半看。可取的一半是「速率/瓶颈/吞吐量」的一阶可视化：Factorio 生产统计屏展示每种物品的产出/消耗速率与时间曲线，社区最常用的 Bottleneck mod 直接在机器上标注「等待输入/输出堵塞」状态[^15^]；教学研究表明，先看见实体在管道中流动、建立定性因果直觉，再做定量决策，符合专家建模系统的方式[^168^]。映射到画布：节点应有「吞吐率/等待上游/输出堆积」状态灯，边上编码消息速率——这正是 6.2.2 的数据面。必须舍弃的一半是物理布局成本：HN 讨论尖锐指出 Factorio 的物理性导致「重构极贵、只有瀑布式重建」，这正是不能引入生产工具的部分[^169^]。因此画布的重排与重构必须零成本（自动布局、拖拽重组、框选折叠），动画服务于调试效率而非游戏感——n8n 2.0 的成功方向恰恰是动画配合「去装饰、更扁平」[^164^]。

### 6.3 层级与聚合

#### 6.3.1 子图折叠与聚合状态徽章

Coordinator 发散的子图规模会快速膨胀，层级折叠是刚需，且行业已收敛到「collapse 成可复用超节点+双击下钻」范式。ComfyUI 2025 年 6 月用 Subgraphs 全面重做失败的 Group Nodes：框选节点「Collapse to Subgraph」成单节点，双击下钻编辑，编辑自动同步所有实例（「修一处 bug，处处修复」）；其关键教训是子图必须有显式的输入/输出端口契约，本质上是「标准 workflow+定义好的接口」[^170^]。LangGraph 侧的证据补足了语义边界：subgraph 只有以编译后的 StateGraph 注册为节点才能在 Studio 中展开，且父子图状态隔离（child/parent keys 互相不可访问）是语义核心[^171^]。对 agent canvas 的推论有二：其一，LangGraph 的 Studio 证据说明只有声明式依赖（注册为节点的编译子图）才能被画布可视化，命令式调用对画布不可见，因此层级组织应引导用户采用声明式子图；其二，折叠节点必须显示聚合状态徽章（运行中/完成数/失败数），呼应第 2 章全局模式「身份四元组+六态徽章+产物快照」的最小信息要求。

#### 6.3.2 循环与条件分支：容器节点内嵌子图，分支出口内联标签

循环的主流解法不是画回边，而是容器型节点内嵌子图：Dify 的循环/迭代节点与 Coze 的循环/批处理节点均把循环体做成内嵌子画布，item/index/loop_result 为循环内局部变量，从而避免画布上出现回边乱线；LangGraph 是例外（允许真实回边，用虚线条件边表达），代价正是大图可读性[^55^]。条件分支的通用做法是分支出口内联标签而非特殊边样式——Dify 的 IF/ELIF/ELSE 各自出口直接挂分支，CrewAI 用 router 节点分流并在边上标注 AND/OR 触发条件与 router 路径名[^55^][^172^]。对 agent canvas 的建议：Coordinator 子图中出现的循环一律渲染为容器节点；条件分支在分支出口放置可编辑的内联标签，边上叠加 AND/OR 汇聚语义；长距离的产物引用可用 ComfyUI 社区验证过的 Get/Set 式「命名引用」替代跨画布长虚线，但需保留 Show links 开关以恢复可见性[^43^]。

## 7. 底层架构：事件溯源、trace 数据模型与 substrate 可视化

前面六章分别讨论了三类节点的窗口形态与边的数据面，本章收束到共同底座：三类节点（产物/操作/对话）在数据层是否真是「三种东西」，节点常驻信息从哪个数据源来，画布引擎选谁、性能预算怎么花。结论先行：三类节点可统一在一条 append-only 事件流的不同投影上；节点信息架构展示「绑定关系」而非状态副本；DOM 渲染架构是唯一可行路线，但必须配虚拟化、LOD（Level of Detail，细节层次）与活内容降级三件套。

### 7.1 统一事件溯源：一条事件流，三种投影

#### 7.1.1 三类节点共享 append-only agent 事件流，各自投影

本调研的跨维度交叉验证将「append-only 事件日志是回放/回滚/审计的地基」列为 High Confidence 共识：LangGraph 工程实践的表述最为直白——每个步骤后持久化 checkpoint、绝不在原地覆盖，「一旦覆盖，你拥有的只是崩溃恢复，而不再是一份记录」（append, not upsert）[^9^][^173^]。在此地基之上，本报告的核心架构推断（Insight 1，置信度 high）是：产物构建、操作执行、通用对话表面上是三种 UI，底层却可以是对同一条 agent 事件流（thought/action/observation/artifact-diff/env-op）的不同投影——产物节点投影 artifact 快照序列，操作节点投影环境画面（VNC 帧、终端字符流、DOM 快照作为富媒体附件），对话节点投影消息序列。NervaFS 的审计流天然扮演事件总线角色：每次 list/read/write 都产生带结构化 reason、target path、binding id、caller 的不可变事件[^14^]。

这一统一的直接收益是「实时」与「回放」同构：回放不是另一套系统，而是同一投影对历史事件区间的重放。开源项目 AgentLens 已验证可行性——实时 span 追加（SSE）与逐帧 scrubber 回放共用同一份 span 存储[^174^]。对产品形态的意义是「跳到某一步看当时的产物/环境状态」（time travel）成为零额外成本的能力，第 2 章的活窗降级阶梯、第 6 章的消息 trace 泳道都只是这条事件流上的又两种投影。

#### 7.1.2 数据模型对齐 OTel GenAI：invoke_agent 根 span，chat/execute_tool 同级子 span

事件模型的词汇表应直接采用 OpenTelemetry GenAI 语义约定：一次 agent run 建模为 `invoke_agent` 根 span，`chat {model}`（LLM 调用）与 `execute_tool {tool}`（工具执行）作为其下的**同级**子 span[^13^]。这里有一条被多家实现反复确认的结构教训：tool span 是 agent span 的孩子，而不是 LLM span 的子级——模型返回工具调用请求时 chat span 即结束，工具执行发生在其后；若把 tool span 嵌入 LLM span，会扭曲时间线并高估模型延迟[^13^]。多 agent 层级则通过子 agent 嵌套为新的 `invoke_agent` 表达，「多 agent handoff 是一棵更深的树，而不是另一种数据」[^13^]。

「类型化 span 树 + trace 级上下文 + session 级分组」已是行业收敛事实：LangSmith 用 run tree 并以 run_type 决定 UI 渲染（llm 渲染消息气泡、tool 渲染参数/结果）[^175^]；Langfuse 的 observation 类型表（span/generation/agent/tool/retriever 等）与 OpenInference span kind 几乎一一对应[^176^]。鉴于 OTel GenAI 约定仍为 Development 状态、属性名可能变动[^13^]，本报告建议「采形状不采字符串」，在映射层隔离具体属性名。另需继承 OTel 的内容/元数据分层——prompt 与消息正文因 PII 风险以 opt-in 方式采集[^13^]，对应到节点 UI 即默认只展示模型、token、耗时、工具名等元数据，消息正文折叠为可展开的隐私敏感区。

### 7.2 节点信息设计：展示「绑定」而非「副本」

#### 7.2.1 节点头 = AgentCard 子集 + env 生命周期态 + substrate 同步状态

在 agent = harness + env + substrate 的三分模型下，节点卡片不需要也不可能展示状态本体，它展示的是三组绑定关系的状态。身份区复用 A2A AgentCard 这一事实标准 schema 的子集（agent id、provider、harness 类型、版本），展开层再放 skills/capabilities/securitySchemes 与签名/attestation 状态；AgentCard 规范本身即明示不建议在卡内放明文 secret[^177^]。env 状态区照搬 E2B 沙盒状态机（Running/Paused/Snapshotting/Killed，含「快照积压时降级为 filesystem-only pause」的中间态）[^178^]。substrate 状态区采用 Kubernetes 的 conditions 数组模式：K8s 把 Pod 状态拆为 phase + conditions 数组（各带 type/status/lastTransitionTime/reason），比单一「健康点」信息量高一个量级[^179^]。映射到节点即 `SubstrateSynced / BindingActive / PolicyCurrent / SnapshotReady` 四个 condition 各为一行布尔态，鼠标悬停展示 lastTransitionTime 与 reason。本调研维度 12 的核心设计原则在此落地：生命周期状态 ≠ 一致性状态，两条线分开渲染[^14^]。

#### 7.2.2 NervaFS 四对象、八 namespace 到节点信息架构的映射

NervaFS 的数据模型由四个核心对象构成：Agent Volume（`/agents/{agent_id}/...`，含 identity/memory/knowledge/skills/communication/data/logs/snapshots 八个 namespace）、Namespace Contract（声明式 mutability class 与 capability）、Runtime Binding（`rb-{8}`，携带 policy revision、cache revision、调用者 OS 上下文与 audit thread）、Provider Adapters（可替换存储后端）[^14^]。下表将其映射为节点全局模式的常驻字段：

| 节点字段（全局模式） | 展示内容 | 数据来源 | NervaFS 对象/namespace 映射 |
|---|---|---|---|
| 标题 + agent id | 用户命名 + `/agents/{agent_id}` | AgentCard / volume 根路径 | Agent Volume（identity）[^14^][^177^] |
| harness 徽标 | harness 类型 + 版本（如 Claude Code 2.x） | Runtime Binding 的 caller OS context | Runtime Binding（`rb-{8}`）[^14^] |
| env 状态点 | Running/Paused/Snapshotting/Killed 色点 | env runtime 状态机上报 | 无（env 侧数据源）[^178^] |
| binding 行 | `rb-a3f1c8 · policy r12 · cache r7` | Runtime Binding 的 revision 字段 | Runtime Binding[^14^] |
| substrate conditions 条 | Synced/BindingActive/PolicyCurrent/SnapshotReady | conditions 数组（K8s 模式） | 由 audit 流聚合派生[^14^][^179^] |
| namespace 健康摘要 | memory/skills 等八 namespace 最近写入时间与写者 | audit 事件流按路径前缀聚合 | Namespace Contract + audit[^14^] |
| 凭证行 | `🔒 OPENAI_API_KEY · via vault · synced 2m ago · rotated 30d` | 引用元信息（值永不出现） | identity 的 capability ref / policy 层[^14^][^180^] |

表中值得注意的三点。其一，七行字段中只有「env 状态点」来自 env 侧，其余全部可由 substrate 与 AgentCard 两个数据源拼出——「展示绑定而非副本」意味着画布无需向每个 env 建立重型数据通道。其二，binding 行的 policy/cache revision 是排查「同一 agent 的不同 env 行为不一致」的第一入口，revision 分叉本身就是可视化信号。其三，需诚实标注边界：NervaFS 当前为 M1 早期版本（v0.3.5），站点强调 local-first、audit 默认开启与 snapshot/bundle handover 迁移，**跨机实时同步协议未披露**[^14^]。因此 Synced condition 现阶段只能由 audit 流聚合派生（如「最近一次跨 env 写入距今多久」），而非来自真实复制协议状态；若产品依赖「多 env 实时同步同一 volume」，需与 NervaFS 路线图对齐。同理，凭证是否为一等 namespace 站点未明示，凭证行先按「引用元信息 + 值级遮罩」挂靠在 identity/policy 层之下[^14^]。

#### 7.2.3 「谁在写」的可视化：audit 反推 + awareness 式 presence

「谁在写」是分布式状态同步中最难可视化的部分。现成答案分两类：CRDT 阵营的 Yjs Awareness 协议天然广播「谁在线、在编辑什么」，已有把 AI agent 注册为 CRDT peer（带 name/color/role/status）与人并列出现在 presence UI 的实践[^181^]；文件系统阵营则普遍「没有协作语义可看」——Letta 的共享 memory block 官方明示 last-write-wins，存储层根本读不出「冲突」，只能展示「最后写入者 + 时间」[^182^]。本报告的推断性建议是组合路线：以 audit 流反推当前写者（近 N 秒内对某 namespace 有 allowed write 事件的 binding/caller 即「活跃写者」），叠加 awareness 式 presence 通道呈现人与 env 的焦点；冲突指示器严格按 substrate 实际语义设计——LWW 语义下画「最后写入者徽标」即可，不要画出不存在的「冲突裁决 UI」。

#### 7.2.4 凭证：只展示引用元信息，值级遮罩，denied 标红

凭证展示的行业惯例是「值永不展示、出现即遮罩」：GitHub Actions 的 `::add-mask::` 可将任意运行时值注册为遮罩对象，此后同一 job 日志流中所有出现处自动替换为 `***`[^180^]。由于凭证可能出现在任意文本（日志、终端回显、工具参数）中，canvas 需要内置同等的**值级**遮罩注册表，而非仅做字段级隐藏。节点上的凭证行只含元信息：名称、来源（vault/env/substrate）、scope（agent/env/run）、上次轮换时间、同步时间、审计链接；值只显示 `***` 或前后 4 位指纹。审计侧直接复用 NervaFS 原生模型——每次 read/write 产生 allowed/denied + reason + binding + caller 事件，按 binding 过滤即可回答「哪个 env 读过这个凭证」，其中 denied 事件单独标红，作为低成本高价值的异常访问信号[^14^]。

### 7.3 画布技术选型与性能预算

#### 7.3.1 DOM 渲染架构是唯一可行路线

节点内要嵌 iframe、视频流、终端这三类活内容，就把渲染架构的选择收敛到了 DOM：纯 Canvas/WebGL 路线（LiteGraph、Excalidraw、Flutter/原生）要么不支持节点内嵌 DOM，要么需要手动同步叠层 DOMWidget 的位置与缩放，工程成本高[^183^][^184^][^185^]。主流候选的对比见下表：

| 框架 | 渲染架构 | LOD / Semantic Zoom | 活内容嵌入 | 画布基础设施 | 许可 |
|---|---|---|---|---|---|
| React Flow 12 | DOM 节点 + SVG 边，CSS transform 缩放 [^186^] | 官方 Contextual Zoom 示例；无内置 LOD 体系 [^2^] | 任意 React 组件；`nodrag`/`nopan` 解决事件冲突 [^187^] | MiniMap/Controls/Panel 内置；视口裁剪 `onlyRenderVisibleElements` [^67^] | MIT [^188^] |
| tldraw SDK | DOM shape 层 + Canvas 2D overlay + 空间索引裁剪 [^1^] | 内置 LOD：zoom 防抖、屏幕尺寸阈值、图片分辨率分级 [^1^] | 一等公民 embed shape：单击选中/双击交互、sandbox 分级 [^5^] | @tldraw/sync 协作、presence、focus mode 最全 [^189^] | 生产使用受 tldraw license 约束，非纯 MIT，条款待核对 [^188^] |
| LiteGraph.js | 单 Canvas2D 即时模式 [^183^] | ComfyUI 实践：低质渲染 zoom 阈值（默认 0.6）[^4^] | DOMWidget 叠 HTML 层，需手动同步变换 [^183^] | 无内置 minimap/协作 | MIT [^188^] |
| Excalidraw | Canvas 2D（rough.js）双 canvas [^184^] | 无 [^184^] | embeddable/iframe 元素类型，曾有 srcdoc XSS CVE [^184^] | 协作 + E2E 加密；扩展性弱 | MIT [^188^] |
| Rete.js v2 | 核心与渲染分离，React/Vue/Angular 渲染插件 [^190^] | 无内置，可用 zoom 信号自建 [^190^] | 取决于渲染器（React 渲染器=DOM，可嵌任意内容）[^190^] | minimap/虚拟化/协作均自建 [^190^] | MIT [^188^] |
| Drawflow | 纯 DOM + SVG 连线，vanilla JS [^191^] | 无；zoom 仅 0.5–1.6 [^191^] | 节点 HTML 任意（可放 iframe）[^191^] | 无 minimap/协作 [^191^] | MIT [^188^] |
| Flutter/原生（canvas_kit、Vyuh Node Flow 等） | Flutter Widget + CustomPainter（Skia/Impeller）；世界/视口双坐标系 [^185^] | Vyuh 宣称 LOD + 视口虚拟化 + viewport culling（厂商宣称，未独立验证）[^185^] | Web 端仅可走 HtmlElementView/PlatformView，存在合成/手势冲突，与活窗架构级冲突（推断，置信度中低）[^185^] | Vyuh 有 minimap/auto-pan；生态远弱于 Web，仅原生桌面/移动目标考虑 [^185^] | 视具体库而定 |

从表中可以看出两个结构性结论。其一，活内容嵌入能力与基础设施完整度正相关地集中在 React Flow 与 tldraw 两家：Rete 选 React 渲染器后嵌入能力等价于 DOM，但 minimap、虚拟化、协作全部要自建；Drawflow 虽可放 iframe，却缺一切大图基础设施，仅适合数十节点级原型；LiteGraph 与 Excalidraw 则与「活窗」存在架构级冲突；Flutter/原生仅当目标平台为原生桌面/移动时才进入候选，Web 目标直接排除[^185^]。其二，最终二选一是本调研遗留的未消解决策点，即冲突区（CZ5）：React Flow 胜在 MIT 许可、节点卡片自由度与生态（Retool、Builder.io 等有大量生产先例），tldraw 胜在 LOD、embed 交互模型、协作栈「开箱最全」，但生产许可条款非纯 MIT、需落地前核对官网最新条款[^188^]。本报告建议原型期双轨验证，以「活窗嵌入密度」和「协作需求强度」为裁决变量。

#### 7.3.2 性能分档与三件套：虚拟化 + LOD + 活内容降级

DOM 架构能成立，靠的是裁剪与 LOD 而非 DOM 本身——ComfyUI Nodes 2.0 把节点从 Canvas 迁到 Vue DOM 后，中大型工作流帧率从 60+ 跌至 5 FPS 以下，官方与社区同时确认「每节点一 DOM 子树」在规模下的风险[^69^]。React Flow 侧的实测分档同样直接：<100 节点默认流畅，100–500 需开视口裁剪，500–1000 需简化节点 DOM，>1000 必须 LOD 或 WebGL 替代；100 个默认节点拖拽即降至约 10 FPS，100 个嵌重内容的节点未优化时仅约 2 FPS、优化后可回 35–40 FPS[^192^]。更隐蔽的瓶颈在 GPU 合成层：ComfyUI 的逐层 profile 显示，性能损耗的约 47% 来自浏览器 GPU 合成器与计算任务的竞争、约 23% 来自实时预览流、约 30% 来自进度事件驱动的 DOM 更新[^68^]——这解释了为什么「所有节点同时直播」在物理上不可行。

![DOM 画布在重节点/活内容下的帧率实测对比](agent_canvas_sec07_perf.png)

上图汇总了两组独立实测：React Flow 在百级节点下即逼近 30 FPS 可交互下限，重内容节点未优化时几乎不可用；ComfyUI 的 DOM 化案例给出「裸 DOM 不可行」的最强反例（60+ FPS → <5 FPS）。两组数据均来自官方 issue/工程博客披露的人工 profile，硬件场景各异、绝对值不宜横向精比，但数量级结论一致：DOM 节点数与活内容数是两条独立的帧率预算线。这指向同一处方——**三件套**：(a) 视口虚拟化（React Flow `onlyRenderVisibleElements` 或 tldraw 空间索引），但全局缩小视图会让所有节点重新进入视口、虚拟化被绕过，10k 节点场景曾因此直接崩溃[^65^]；(b) 语义 LOD，按「节点屏幕像素尺寸」而非绝对 zoom 设阈值（tldraw 模式：`shape.w × zoom < 50px` 时渲染简化版），zoom 值需防抖以避免缩放中途全图重渲染[^1^]；(c) 活内容降级阶梯，低 zoom/全局模式降级为静态缩略图或心跳帧，与第 2 章的活节点配额衔接。另有一个已知约束：被裁剪或 `display:none` 的 iframe 会被浏览器冻结，visibility/opacity/clip-path 等替代手段全部失效，唯一可靠的保活法是保持渲染并用遮罩盖住——被点亮的活节点必须豁免疫裁剪[^66^]。

#### 7.3.3 画布基础设施：minimap、presence 与深缩放

三处基础设施有明确的正反例可循。minimap 必须用 Canvas 画像素点而非渲染真实节点：React Flow 默认 MiniMap 在 10k 节点时是「致命」热点，生产实践改用 HTML5 Canvas 自绘像素簇、零 DOM 开销[^65^]；ComfyUI 自研 minimap 因每帧全量扫描并序列化所有连线被点名为性能热点[^68^]。presence/协作光标走独立通道：tldraw sync 的 presence 记录仅存内存、不持久化、按 session 作用域，服务端 60fps 合批广播，协作光标渲染在 canvas 之上、UI 之下的独立 DOM 层[^189^]——这正是 7.2.3 节 presence 可视化的传输底座。深缩放方面，全局模式看全图时 minZoom 需设到 0.05–0.1 级，且 fitView 与 minZoom/maxZoom 必须一致，否则开始缩放瞬间会发生视口跳变[^193^]。最后，专注模式实现复用 2.3.1 确立的「移动 DOM 节点不重挂载」铁律。这与 7.1 的实时/回放同构原则共同保证「放大看清」与「状态连续」不互斥，也为第 8 章落地路线划出画布层的决策边界。

## 8. 落地建议、决策点与未决问题

本章将前七章结论收束为可执行的工程排序。排序原则是「证据强度 × 实现成本」：经交叉验证确认且已有成熟实现的项目进入 MVP；证据充分但需自行拼装管线的进入进阶期；构成差异化空档、但整体形态尚无先例的排入差异化期。决策点逐条给出建议与依据引用，真实知识缺口在 8.3 诚实标注，不给虚假确定性。

### 8.1 分阶段落地路线

#### 8.1.1 MVP：DOM 画布 + 三态 LOD + noVNC 操作窗 + 产物 iframe 预览 + 事件流埋点

五项全部来自 High Confidence 结论。**DOM 画布**是内嵌活内容的唯一可行架构，ComfyUI DOM 化翻车（60+ FPS 跌至 5 以下）证明的是「裸 DOM 不可行」而非「DOM 不可行」，故 MVP 第一天就须配齐虚拟化、LOD、活内容降级三件套[^68^]。**三态 LOD** 先只实现全局摘要卡与默认卡片两条渲染路径——按节点屏幕像素尺寸设阈值、zoom 防抖、集中式 ViewModeManager 下发档位，均为 tldraw 官方文档沉淀的现成模式[^1^]。**noVNC 操作窗**采用四方独立验证的 noVNC + websockify + x11vnc/Xvfb 组合，整条链路仅三个组件[^111^]。**产物 iframe 预览**沿用 Anthropic Artifacts 的行业默认：空 sandbox 逐项加权限、严格 CSP、srcdoc 禁止拼接不可信字符串[^88^]。**事件流埋点**是唯一「只投入、不兑现」的项：对齐 OTel GenAI 语义（invoke_agent 根 span，chat/execute_tool 同级子 span），append-only 落盘但本期不做回放 UI——「append, not upsert」的地基错过即不可逆[^13^]。MVP 的显式裁剪同样重要：不做回放、不做多人协作、弱链接只画静态虚线，交互权移交仅覆盖 VNC takeover。

#### 8.1.2 进阶：事件流回放时间轴、annotation 管线、审批 Inbox、活节点配额调度、Coordinator 双向锚定

进阶期是 MVP 所埋结构的「第一次消费」。**回放时间轴**兑现统一事件溯源：回放 = 同一投影对历史事件区间的重放，AgentLens 已验证实时追加与 scrubber 回放可共用同一份 span 存储[^174^]；本期只做 time travel 第一档「快照还原查看」，终端侧复用 asciinema cast（体积为视频 1/100~1/1000，3.0 已验证「录制 = 实时管道旁路」）[^133^]。**annotation 管线**按「point first, then describe」范式实现，标注以结构化 envelope（selector + bbox + intent + 状态机）回传 agent[^103^]。**审批 Inbox** 把四态决策聚合为队列，且必须实现超时兜底：LangGraph interrupt 默认无限期等待，生产实践是外部 sweeper 扫过期 checkpoint、按风险分级默认放行或拒绝[^62^]。**活节点配额调度**把降级阶梯（全帧 → 低帧 → 心跳帧 → 快照）接入 ViewModeManager：默认模式同时直播设上限（如 ≤4 个），隐藏 iframe 必被浏览器冻结（2.2.3），被点亮节点须豁免疫裁剪[^66^]。**Coordinator 委派卡片与子节点双向锚定**（Insight 7，见第 5 章）：Coordinator 对话中的委派卡片与其生成的子节点建立双向跳转锚点，构成对话↔图结构双生视图的入口。

#### 8.1.3 差异化：弱链接数据面、知识沉淀管线、time travel、多人协作

差异化期对应 Insight 1/4/5 与第 1 章的行业空档。**弱链接数据面**（Insight 4）：虚线边挂载消息速率、产物版本引用与滞后告警（上游 v5、下游仍消费 v2 时触发），排查模式点击边打开消息 trace 泳道；n8n 的 ai_tool 虚线已证明线型可承载真实执行语义，而竞品图谱中无产品在边上挂载动态运行信息[^17^]。**知识沉淀管线**（Insight 5，medium-high）：annotation、接管、审批拒绝分别转化为偏好样本、runbook 草稿、风险策略样本，以「知识草稿」进入 substrate 经人审后召回——Devin Knowledge 的「建议 → 人审 → 入库 → 召回」是环节范本，但整体形态无完整先例，故允许失败回滚[^194^]。**time travel**（Insight 1）推进第二档（checkpoint 重放 + 模型响应录制）与第三档（Crab 论文的分级环境 checkpoint）[^9^]。**多人协作**（工程扩展项，无 Insight 直接对应）先落 presence 通道（tldraw sync 或 Yjs awareness 式），审批 claim/lock 属未决问题（8.3.2），需自行设计[^189^]。

### 8.2 关键决策点

#### 8.2.1 React Flow vs tldraw：原型期双轨验证，许可与嵌入自由度权衡

画布引擎是交叉验证遗留的唯一未消解的冲突区（CZ5），本章补充核实了许可事实：tldraw SDK 4.x 起改为 source-available 自定义许可——开发免费、生产必须持有 license key，选项为免费 hobby 许可（非商用、强制水印）或商业许可（无公开价目，另有 100 天试用），且 SDK 内置密钥校验，条款以官网最新为准[^195^]，第三方报道 HN 报价约 6000 美元/年[^186^]；React Flow 为 MIT，生产先例充足[^186^]。裁决变量由此收敛为两个：协作需求强度（tldraw 的 sync/presence/embed 交互模型开箱最全）与许可成本接受度。建议：原型期双轨验证「活窗嵌入密度」这一共同前提；含商用 SaaS 交付且不愿承担许可成本则默认 React Flow、自建 LOD 与 embed 交互（模式均有文档、工作量可估）；协作是核心卖点且预算允许时再评估 tldraw 商业许可。双轨期应限定在原型阶段，避免双栈维护蔓延。

#### 8.2.2 活内容上限策略、审批超时默认策略、回放存储格式

| 决策项 | 候选选项 | 建议 | 依据 |
|---|---|---|---|
| 画布引擎 | React Flow（MIT）/ tldraw（生产需 license key） | 原型期双轨验证；商用交付默认 React Flow，协作密集且预算允许时评估 tldraw 商业许可 | 冲突区（CZ5）未消解；tldraw 4.0 起生产需密钥、hobby 许可强制水印 [^195^][^186^] |
| 活内容上限策略 | 全部直播 / 固定配额 / 可调配额 + 降级阶梯 | 默认模式 ≤4 节点直播，其余沿降级阶梯退档；配额为运行时可调参数 | GPU 合成器竞争占慢化因素约 47%；隐藏 iframe 必冻结 [^68^][^66^] |
| 审批超时默认策略 | 无限等待 / 一律放行 / 一律拒绝 / 风险分级 | 外部 sweeper + 风险分级：低风险放行、高风险阻断；「人不在」作为一等公民结果上报 | LangGraph 无内建 TTL，框架永不唤醒挂起的 interrupt [^62^] |
| 回放存储格式 | 录屏视频 / 事件流 + 富媒体附件 / 自包含 trace 包 | 事件流为主索引，asciinema cast 与 rrweb 快照为附件；审计场景导出 trace 式自包含包 | 字符流体积为视频 1/100~1/1000 且可 grep；trace.zip 纯前端打开、数据不出浏览器 [^133^][^132^] |

解读：四个决策点呈两种性质。画布引擎是「不可回头的选型」，故保留双轨验证期收集实据，其裁决变量（协作强度、许可成本）是产品侧变量——技术侧两候选均能承载活窗密度。其余三项是「参数化的工程策略」，共同特征是默认值必须有外部兜底而非依赖组件自觉：配额兜底浏览器冻结行为，sweeper 兜底框架的无限等待，事件流格式兜底回放的可检索性，分别对应第 2 章（2.2.3 GPU 合成开销）、本章 8.1.2（interrupt 无 TTL）与第 4 章（4.3.2 像素不可检索）论证过的约束。三者均留有调节旋钮（配额数值、风险阈值、附件档位），落地后应按真实负载与误报率回校准，而非一次性设定。

### 8.3 未决问题

以下为交叉验证确认的「领域尚未公开的知识缺口」，只给过渡策略，不给虚假确定性。

#### 8.3.1 NervaFS 跨机实时同步协议未披露

NervaFS 当前为 M1 早期版本（v0.3.5），主打 local-first、audit 默认开启与 snapshot/bundle handover 迁移，**跨机实时同步协议未披露**[^14^]。直接影响节点状态区设计：`SubstrateSynced` condition 现阶段只能由 audit 流聚合派生（如「最近一次跨 env 写入距今」），而非真实复制协议状态。过渡策略：若产品依赖多 env 实时同步同一 volume，须与 NervaFS 路线图对齐后再承诺；否则以 audit 流 + awareness 式 presence 组合自建展示语义，UI 文案避免暗示强一致性。

#### 8.3.2 凭证一等 namespace、多人审批 claim/lock、PPT 结构 diff

**凭证是否为 NervaFS 一等 namespace**：站点未明示，节点上先按「引用元信息 + 值级遮罩」挂于 identity/policy 层——名称、来源、scope、轮换时间可见，值永不出现，并内置 GitHub Actions `add-mask` 式值级遮罩注册表覆盖日志与终端回显[^14^][^180^]。**多人审批的 claim/lock/通知机制**：现有开源 HITL UI 均无先例，既是空白也是机会点；协作期需自行设计，可借鉴审阅队列治理中的 reservation timeout（防条目被闲置审阅者锁死）与高风险二次复核[^62^]。**PPT 类产物的结构 diff**：资料稀缺（dim05 标注为外推），落地时先以视觉回归四模式（side-by-side、wipe、onion-skin、pixel-diff）兜底版本对照，结构级 diff 作为补充研究课题，不作为功能承诺[^101^]。

# 执行层级二次收拢

本轮针对用户红框中的剩余碎片：第一版只合并整个消息都是工具/思考的条目，没有处理“思考＋正文＋工具”的混合消息。

## 行为与边界

先把混合助手消息按正文/执行边界拆为显示片段，再合并同 run 的邻接执行片段。原消息的开头思考可以加入前一执行组，末尾工具可以加入后一执行组；正文、用户消息、错误、未关联活动与不同 run 都保留边界。`sourceTurns` 保留原始记录，不凭展示关系推导新的执行关联。

摘要只保留标题、工具数量和就近状态，类型统计/思考段数放到展开层。纯思考使用“思考过程”。执行组没有时间戳页脚；同一原消息拆出的正文只有最后一段保留页脚，复制仍包含完整原文。

## 本轮验证

- 4 个新增单测检查混合片段顺序/来源、边界、缓存/key、页脚归属和精简摘要。
- 2 个新增浏览器用例复现红框结构，并检查完整正文复制。
- 合成场景：24 工具 → 思考/正文/1 工具 → 69 工具 → 思考/回答，结果是两个执行组（24 / 70），没有孤立思考入口。
- 收起行高度 ≤40px；状态贴近标题；工具下无 footer/time。流式追加最终正文时，已打开的 tool-80 DOM 和输出保持。
- 桌面与 390px 都通过自动截图/几何检查，且两张截图已在 PI-Desktop 内置浏览器中目视确认；不把上一版目视通道失败延用为本轮结果。
- 最终全量结果见 `verification.json`；浏览器为 HTTP/WS fixtures，不是新模型或真实工具执行证明。
